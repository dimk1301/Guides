What is Spec-Driven Development?

Spec-Driven Development (SDD) is the structural successor to "vibe coding" — the term Andrej Karpathy coined in February 2025 for the ad-hoc, prompt-and-pray loop of throwing natural-language instructions at a model until something works. By mid-2026 it had become clear that vibe coding does not hold up once real users, real security requirements, and real teammates are in the loop.

SDD is a methodology in which a written specification is treated as the primary, executable artifact of a software project, and code is a regenerable output produced from that spec by humans, AI agents, or both. The specification file, not the eventual codebase, becomes the single source of truth. Instead of describing a system brick-by-brick through an endless chat, you hand an autonomous agent a complete engineering blueprint. It builds against that blueprint, and when requirements change, you edit the spec and regenerate the code rather than hand-patch the output.

As Birgitta Böckeler of Thoughtworks puts it, SDD fundamentally means that "the specification is the single source of truth, and the code is a generated artifact." This shifts the developer's role from writing every line of code to maintaining the authoritative document that defines what the system should do.

The problem it actually solves

Improvising via chat is great for a prototype and dangerous for anything that has to survive contact with production. Models are extraordinary pattern-completers and unreliable mind-readers. Left unconstrained, ambiguity in your intent does not stay small — it compounds into architectures nobody chose on purpose, missing security controls, unhandled edge cases, and thin-to-nonexistent test coverage. Teams have taken to calling this failure mode "automating the creation of legacy mess." A written spec turns fuzzy intent into a deterministic contract the agent cannot quietly drift away from. The lever for output quality shifts from prompt cleverness to spec quality.

Loop Engineering vs. Harness Engineering

A useful way to think about SDD is to distinguish two layers: loop engineering — the design of the iterative cycle that drives the agent toward a goal (your Specify → Plan → Tasks → Implement cycle) — and harness engineering — the environment built around the agent (your Constitution, steering files, tool permissions, review gates, and recovery patterns). The loop governs what the agent does on each pass; the harness governs what it is allowed to touch, how it recovers from failure, and how you observe what it did. Confusing the two causes predictable failures — a weak harness lets an agent edit production configs, a weak loop makes agents stall. SDD fixes both, and naming the distinction helps you explain why SDD works to skeptical teammates.

The Continuum of Commitment

Rolling SDD into a real engineering team is not binary — it sits on a spectrum of how much authority you are willing to hand the spec. Most teams start at level one and drift toward level two; very few production shops run level three today. As Thoughtworks' Birgitta Böckeler notes, "all SDD approaches and definitions I've found are spec-first, but not all strive to be spec-anchored or spec-as-source."

LEVEL 1

Spec-First

A well-thought-out spec is fully drafted before engineering starts. The agent writes the baseline; from there, the human developer reviews, edits, and maintains the code by hand. Highest risk of the spec going stale the moment the first hotfix lands.

LEVEL 2

Spec-Anchored

Specs are treated as living, long-term artifacts that evolve alongside new features. Humans actively keep code and spec synchronized, so both remain aligned through the entire maintenance lifecycle — not just at launch.

LEVEL 3

Spec-As-Source

The specification is the only file humans edit. Generated code carries markers like // GENERATED FROM SPEC — DO NOT EDIT. Application code is treated as a compiled, transient byproduct — closer to how a build treats a .class file than how a team treats a repo.

Watch For

Level 3 is the one vendors talk about most and teams actually run least. Treat it as a destination worth understanding, not a default starting point — most production teams get the bulk of SDD's value by simply reaching Level 2 and staying there.

When to Use SDD — and When to Skip It

Before you invest in the full loop, decide whether you need it at all. SDD is structural reliability; for small tasks it's a sledgehammer to crack a nut. Use this decision framework to pick the right tool for the job.

Reach for Spec-Driven when:

  • You are writing production systems meant to scale and be maintained long-term.
  • Multiple engineers, or multiple parallel agents, work the same codebase at once.
  • You must enforce security profiles, data constraints, compliance rules, or design tokens precisely.
  • The system involves migrations, multi-service topologies, or intricate state machines.

Default to Vibe Coding when:

  • You are building throwaway code, isolated proofs-of-concept, or rapid wireframes.
  • The task is visual and needs fast, intuitive tweaking rather than a locked spec.
  • It is a minor bug fix — a full pipeline here is overkill.
  • You are exploring an unfamiliar stack and do not yet know what you actually want.
A Practical Test

One heuristic experienced SDD practitioners use cuts through the ambiguity fast: if you would be annoyed to find the agent interpreted your requirement differently than you meant, write the spec. If a quick follow-up prompt would fix it just fine, skip the spec and prompt directly. It is a five-second gut check, and it is usually right.

The Honest Limits

Even when SDD is the right call, be aware of where it currently breaks down.

  • Brownfield adoption gap: SDD shines on greenfield projects. Dropping a full pipeline onto a large legacy codebase in one go rarely works — adopt feature by feature, not as a big-bang rewrite. Both tools have onboarding steps (see Sheet 12), but treat the first few brownfield specs as trust-building exercises.
  • Markdown Monster risk: Complex spec workflows can produce documentation overhead instead of clarity. If a simple change spawns hundreds of planning files, you are spending more time reviewing prose than code. The fix: archive specs after merge, delete stale ones after 90 days, and keep specs just-in-time (see Sheet 08).
  • Semantic diffusion: "Spec" is often used as a synonym for "a detailed prompt." That is not SDD — true SDD requires an execution engine that treats the specification as an actionable, verifiable source of truth, not just a longer prompt.
  • Heavy-upfront-planning critique: Thoughtworks' Technology Radar flags a risk of SDD tilting back toward big up-front specification — the anti-pattern Agile spent decades pushing away. SDD is compatible with Agile when specs stay living, lightweight artifacts updated inside normal sprints. The moment they calcify into Waterfall-style documentation, you have lost the point.
  • Human-gates debate: Some argue that as agents improve, manual approval gates become pure friction. The counter-argument: production software carries risk, compliance, and legal accountability that someone has to own. Human gates exist not because agents cannot do the work, but because someone must be liable when it is wrong.
Bottom Line

SDD is a genuine improvement over unstructured prompting for anything production-grade — but it is a discipline, not a silver bullet. It still requires someone to write a good spec, and a bad spec compiled perfectly is still a bad system.

Core Workflow: The 4-Phase Loop

The SDD loop is a collaboration between you (the human) and the AI agent. Each phase has a clear division of labour: the agent drafts, you review and approve. Here is exactly who does what.

Pre-Phase 0: Spike the Unknowns

If the feature contains technical uncertainty — a new API you have never integrated, an unproven performance path, an unfamiliar library with opaque behavior — run a throwaway spike before you write the spec. The spike is deliberately ugly: it is not meant to ship, it is meant to answer one question: "does this approach work?"

  • Keep it small. The spike should take less than two hours. If it takes longer, the uncertainty is too broad — split the problem.
  • Comment heavily. Mark every line that proves the approach works and every line that is intentionally incomplete (// PROVEN: this call returns the expected shape).
  • Store the reference. Save the spike in _spec/spikes/reference/<name>/ and link it from the spec's new Reference implementation section (see Sheet 05).
  • Bin or refactor. Once the spike proves the approach, either delete it or refactor the proven parts into the real implementation. Do not ship the spike as-is.

A working reference stops the agent from hallucinating behavior that "should" work but does not. It also gives you a concrete fallback when the agent's generated code fails: you can compare its approach against the reference and see exactly where it diverged.

When to Spike

Spike when you would say "I'm not sure if this will work" out loud. Do not spike for straightforward CRUD, known libraries, or patterns your team has already validated.

PhaseWhat the AI Agent doesWhat You (the Human) doesHandoff / Checkpoint
1. Specify Drafts the initial spec, asks clarifying questions, flags gaps Writes the initial description, reviews the drafted spec, answers questions, approves it You say "yes, proceed" — spec is locked
2. Plan Reads the spec, generates a technical architecture plan Reviews the plan, checks feasibility, approves or requests changes You say "yes, proceed" — plan is locked
3. Tasks Breaks the plan into an ordered checklist of micro-tasks Reviews the task list, checks completeness, approves it You say "yes, proceed" — task list is locked
4. Implement Executes the tasks (Kiro runs independent tasks in parallel waves; Claude Code runs them sequentially unless you configure otherwise) Reviews the targeted diffs, validates against the spec, approves the merge You review each change; agent loops back if you request fixes
The Golden Rule

The agent never moves to the next phase without your explicit approval. You are the decision-maker. The agent is the executor. This is what prevents the "automated legacy mess" problem — you stay in control.

Phase 1 — Specify & Clarify (The Teaching Phase)

Phase 1 is where the loop earns its trust. The rest of the phases follow the same rhythm — draft, review, approve — but Phase 1 is where ambiguity is caught before it becomes architecture.

What the AI Agent does:

  • Reads your initial description (a few sentences about what you want to build).
  • Drafts a structured spec.md with functional requirements, constraints, and success criteria.
  • Runs a clarification pass — it identifies logical gaps, contradictions, and ambiguous statements.
  • Asks you specific questions to fill in the blanks ("What should happen if the API key is invalid?", "How many requests per second do you expect?").
  • Updates the spec based on your answers.

What You (the Human) do:

  • Write the initial description — just a few sentences about what you need.
  • Read the draft spec the agent produces.
  • Answer the agent's clarification questions.
  • Review the final spec and explicitly approve it before the agent moves to Phase 2.
Example Conversation

You: "Build a token-bucket API rate limiter middleware."
Agent: "I'll draft a spec. How many requests per second? What should the response be when rate-limited?"
You: "100 per second. Return 429 Too Many Requests."
Agent: "Here's the complete spec. Does this cover everything?"
You: "Yes, proceed." → Phase 1 complete.

Phases 2–4 — Same Rhythm, Different Artifacts

Once Phase 1 is locked, Phases 2–4 follow an identical pattern: the agent produces a draft, you review it against the prior phase's output, and you explicitly approve before the agent continues. The only difference is the artifact being produced.

PhaseAgent OutputYour Review Focus
2. Plan plan.md — architecture, dependencies, data flow, risk assessment Does the technical approach fit your stack? Are security liabilities flagged? Does it map every requirement to an implementation strategy?
3. Tasks tasks.md — ordered checklist of micro-tasks, each with definition of done and verification instructions Are all acceptance criteria covered? Is the order collision-free? Can each task be verified independently?
4. Implement Targeted diffs — small, focused code changes, one per task, with tests. Kiro executes independent tasks in parallel waves; Claude Code runs them sequentially unless you configure otherwise. Does the diff match the plan? Does it reuse existing patterns? Does it satisfy the spec's EARS requirements?

Greenfield vs. Brownfield: Where Phase 1 Actually Starts

The four phases are the same either way, but Phase 1 starts from a different place. Greenfield — there is no existing code to contradict, so the spec you write is genuinely the first source of truth. Brownfield — the codebase already has an implicit spec: however it actually behaves today, documented or not. Skip acknowledging that, and Phase 1 will happily draft requirements that quietly conflict with what is already shipped. Both tools have a specific fix for this — see Sheet 12 for the exact commands.

The Verifier Pattern

The most underused refinement: assign a separate agent to verify the implementing agent's work rather than trusting it to self‑check. Treat "verifier" as a distinct role in your pipeline — the same way you would not let one engineer be the only reviewer of their own pull request. See Sheet 09 for a reusable reviewer prompt.

How This Plays Out in Practice

Kiro CLI: The built‑in /spec agent automates this entire loop. You run /spec new, the agent produces requirements.md. You review and type "proceed" — agent moves to design.md. You review and type "proceed" — agent moves to tasks.md. You review and type "proceed" — agent runs /spec run and executes the tasks, showing you each diff as it goes. Independent tasks run in parallel waves based on dependency graph.

Claude Code: You bring your own workflow, but Claude has a built-in Plan Mode (Shift+Tab twice, or /plan) — a read‑only planning state where Claude proposes a plan before touching files, which you approve or reject. This provides a native phase-gate even if you don't use custom commands. You can layer additional structure via .claude/commands/.

Token Economics Reality Check

Multi-phase agentic workflows can burn significant tokens. A full 4-phase loop with a large spec may consume a meaningful amount of tokens before code is written — for a 10‑minute bug fix, that's overkill; for a 2‑week feature, it's cheap insurance against architectural drift. Let the scope decide whether you pay the overhead.

Side benefit: A precise spec often lets you drop to a lower‑tier model (e.g., Haiku) for implementation and still get output quality comparable to a top‑tier model running on a vague prompt. The spec carries the precision; the model just executes. This can meaningfully reduce token costs without a noticeable drop in code quality.

File Anatomy & Templates

The 4-phase loop produces three files. Without a standard structure, every team invents its own format and fragments. Here are the mandatory sections for each file — copy these templates directly into your repo and fill them in.

spec.md / requirements.md
The Feature Contract
  • Title — One-line description of the feature.
  • Background — Why this feature exists. Business context, user pain, or system gap.
  • EARS Requirements — Numbered list of When/While/If/Where + shall clauses. One obligation per sentence.
  • Non-goals — What this system explicitly will not do. Prevents overengineering and scope creep.
  • Assumptions — Decisions already made that the model should not silently re-decide (e.g., "cursor-based pagination, not offset").
  • Constraints — Hard limits the agent cannot violate (performance budgets, banned dependencies, compliance rules).
  • Reference implementation — Link to a spike or existing code that proves the approach works.
  • Test Plan — Named tests with exact inputs and expected outputs, written before the implementation plan. Example: Test T1: POST /api/bulk with 10,001 rows → returns 413 in < 200ms.
  • Acceptance Criteria — Verifiable outcomes that prove the feature works. Map 1:1 to EARS requirements and Test Plan entries.
  • Out of Scope — Explicitly excluded functionality to prevent scope creep (broader than Non-goals).
plan.md / design.md
The Technical Blueprint
  • Architecture Decision — The chosen approach and why alternatives were rejected.
  • Data Flow — How data moves through the system for this feature. Diagram or bullet list.
  • Component Design — New files, modified files, and their responsibilities.
  • Dependencies — New libraries or services required, with justification.
  • Risk Assessment — Security liabilities, integration pain points, and mitigation strategies.
  • Test Strategy — Unit, integration, and edge-case coverage plan.
tasks.md
The Execution Checklist
  • Task ID — Sequential number (T01, T02...) for traceability.
  • Description — One-sentence objective.
  • Definition of Done — Exact criteria that mark this task complete.
  • Verification Command — The test or lint command that proves this task works.
  • Effort — Rough sizing (S/M/L) to catch tasks that are too large.
  • Dependencies — Which tasks must finish before this one starts.

Granularity rule: Each task should be completable in 2–5 minutes of focused work. If a task exceeds that, split it. The agent should never be asked to hold enough context for a 30‑minute task in a single pass.

Why These Sections Matter

Skipping a section does not just make the file shorter — it makes the agent guess. No Constraints section means the agent proposes whatever dependency is statistically nearest. No Out of Scope means the agent quietly implements adjacent features it thinks are "obvious." No Verification Command in tasks means the agent decides when it is "done" — which is usually too early. No Non-goals means the agent optimizes for features you never asked for. No Assumptions means the agent re-decides technical choices you already made, wasting tokens on re-architecture. No Test Plan means the agent writes tests that prove the code works but not that it solves the right problem.

Start With a Skeleton

Do not wait until you have perfect content to create the file. Create the skeleton with all headers first, then fill in the EARS requirements. The skeleton acts as a checklist: if a header is empty, you know the spec is not ready for review.

The Constitution & Standing Context

Every project needs two kinds of document: temporary specs that exist for one feature, and standing rules that apply to every change. The Constitution is your immutable foundation — the second kind.

As Birgitta Böckeler puts it, "general context are things like rules files, or high level descriptions of the product and the codebase… whereas specs [are] only relevant to the tasks that actually create or change that particular functionality." That standing-rules document is what this section covers.

What the Constitution Covers

A Constitution defines non‑negotiable principles that apply to every change — testing philosophy, security baselines, code style, and opinionated technology choices. This ensures organizational standards are baked into every project from the start.

constitution.md (generic template)
# Project Constitution — immutable principles
- All database mutations must use explicit transaction boundaries.
- All public endpoints must include active rate-limiting middleware.
- Unit tests are required for any newly created utility method.
- Write tests before implementing any business logic (TDD discipline).
- No raw SQL in controllers — all queries go through the repository layer.
- Secrets must be injected via environment variables, never hard-coded.

How the Constitution Fits into the Loop

  • You write it once at the start of the project.
  • The agent reads it at the beginning of every session — it is part of its permanent memory.
  • Every phase respects the Constitution: the agent will not propose a plan that violates it, and you use it as your own checklist during reviews.

Workspace Isolation

Before the agent writes a single line of code, ensure it works on a clean branch or git worktree with a verified green test baseline. A dirty workspace or failing baseline makes it impossible to tell whether a test failure is from the new code or pre‑existing debt.

  • Why it matters: If the agent starts from a broken state, every fix it applies is a guess. You will burn tokens on regression fixes that should never have been the agent's problem.
  • How to do it: Use git worktree add ../feature-name main to create a fresh, isolated workspace. Run tests before the agent starts — if they fail, fix them first.
  • Tool support: Superpowers enforces this as a mandatory first step. Kiro CLI's /spec new does not automatically create a worktree, but you should treat it as a manual pre‑phase ritual.

This is harness engineering at its most basic: if you cannot trust the baseline, you cannot trust the diff.

Agent Permissions and Blast Radius

Giving an agent write access to your repo is a significant trust decision. Protect yourself with these harness practices:

  • Least privilege: Restrict the agent's tool access to only what it needs for the task. In Claude Code, use permissions in CLAUDE.md to deny dangerous commands (e.g., rm -rf, sudo). In Kiro, the agent runs in a sandboxed environment by default, but you can further restrict via steering files.
  • Prompt injection awareness: If the agent fetches external content (e.g., from a URL or file), that content could contain instructions that override your spec. Treat fetched content as untrusted — validate or sanitize it before feeding it into the agent's context.
  • Diff review, not blind trust: The scorecard (Sheet 09) is your primary defense. Never merge a generated diff without reviewing it — even if all tests pass.

Implementation by Tool

Kiro CLI — Steering Files

Store your Constitution in steering files inside .kiro/steering/. For example, put architecture rules in tech.md, structural rules in structure.md, and product rules in product.md. Since steering files are always loaded in every interaction, they automatically enforce your immutable rules on every change — no extra configuration needed.

.kiro/steering/tech.md — Kiro's Constitution
# Technology Constitution
- All database mutations must use explicit transaction boundaries.
- All public endpoints must include rate-limiting middleware.
- Write tests before implementing any business logic.
- All external API calls must have a 5-second timeout and circuit-breaker fallback.

Claude Code — CLAUDE.md

Place your Constitution directly in CLAUDE.md, which is read at the start of every session. For larger rulebooks, keep a separate constitution.md and reference it in CLAUDE.md using the @constitution.md syntax. This ensures Claude applies your rules to every task it touches.

CLAUDE.md — Claude's Constitution
# Project Constitution (loaded every session)
- All database mutations must use explicit transaction boundaries.
- All public endpoints must include rate-limiting middleware.
- Write tests before implementing any business logic.

# Reference a separate constitution file if it grows large
@constitution.md

Brownfield Bootstrapping

Both tools can generate a starter Constitution from an existing codebase instead of writing it blank:

  • Kiro: Use Generate Steering Docs (IDE button, CLI, or Web) to scan the repo and auto-draft product.md, tech.md, and structure.md from what is actually there.
  • Claude Code: Run /init in the repo before writing anything by hand — it detects your build system, test framework, and code patterns, and drafts a starter CLAUDE.md you refine from there.

Either way, do this before your first spec, not after — it is what stops Phase 1 from drafting requirements that quietly contradict how the codebase already works.

Constitution = Persistent Context

Whether you use Kiro's steering files or Claude's CLAUDE.md, the Constitution is your team's living rulebook. It outlasts any single feature spec and ensures every AI session starts with the same non‑negotiable standards. Update it rarely — treat it like a real constitution, not a daily checklist.

Writing Specs with EARS

EARS — the Easy Approach to Requirements Syntax — is the bridge between human intent and machine execution. It forces ambiguity out of requirements by replacing prose with structured clauses an LLM can parse as cleanly as a compiler parses code.

Developed by Alistair Mavin and adopted by aerospace and automotive engineering, EARS has five keywords that cover virtually every functional requirement you will write: When, While, Where, If, and Shall. The syntax is deliberately rigid because rigidity is exactly what prevents an agent from hallucinating intent.

When

Event-Driven Requirements

Use When for discrete triggers. "When the user clicks Submit, the system shall validate the payload." The event is singular and unambiguous.

While

State-Driven Requirements

Use While for continuous conditions. "While the connection is open, the system shall heartbeat every 30 seconds." Describes sustained behavior, not a one-off.

If

Conditional Requirements

Use If for branching logic. "If the API key is invalid, then the system shall return 401 before evaluating the rate limit." Nests inside When or While.

Where

Contextual Requirements

Use Where for scoped behavior. "Where the request originates from an internal subnet, the system shall bypass the rate limiter." Sets boundaries.

Why EARS matters for SDD

Large language models are pattern-completers. When you feed them structured patterns, they complete the right pattern. When you feed them vague prose, they complete whatever pattern is statistically nearest — which may not be what you meant. EARS gives the agent a grammar to follow, not just a topic to riff on.

As a practical rule: if you cannot restate a requirement as a When/If/While/Where clause followed by "the system shall," the requirement is not ready for an agent. It still has ambiguity that will compound into architectural drift.

From Vague to Verifiable

Vague (what not to write)EARS-compliant (what to write)
"The API should handle rate limiting." "When a client exceeds 100 requests in a 1-second window, the system shall return HTTP 429 and include a Retry-After header."
"Users must be authenticated." "When a request is received without a valid JWT, the system shall return 401 and shall not process the payload."
"The system should be fast." "When the database query returns more than 10,000 rows, the system shall paginate the response and shall return the first page within 200ms."
"Log errors properly." "If an unhandled exception occurs, the system shall write the stack trace to stderr with a UTC timestamp and shall return 500 to the client without exposing internal paths."

Common EARS Anti-Patterns

  • "Shall be able to" — Describes capability, not obligation. The agent may implement the feature as optional. Use "shall" alone for mandatory behavior.
  • "Shall consider" — Unverifiable. How do you test whether something was "considered"? Replace with a concrete action.
  • Multiple requirements in one sentence — "When X happens the system shall do Y and Z and also notify Q." Split into atomic sentences. One clause, one obligation.
  • Missing the trigger — A requirement that starts with "The system shall..." but never says When or If leaves the agent guessing about invocation context.

Nested Conditions

Real requirements rarely fit a single keyword. EARS supports nesting:

Nested EARS example
# Good: nested, unambiguous
When a payment request is received,
  If the account balance is sufficient,
    the system shall debit the amount and shall return 200.
  If the account balance is insufficient,
    the system shall return 402 and shall log the attempt.

# Bad: ambiguous ordering and missing branch
The system should process payments and handle errors.
Quick Reference

Before you approve any spec.md, run the EARS lint: can every requirement be prefixed with When/While/If/Where and end with a single "shall" action? If not, send it back for rewriting. This one habit prevents more agentic drift than any prompt-engineering trick.

Spec in Scrum & Kanban (Optional — for team leads)

A spec that lives outside your delivery rhythm is a spec that dies. SDD does not replace Agile — it needs to be wired into your existing ceremonies and board states. This section is aimed at team leads; if you're an individual developer, you can skip to the next sheet.

Scrum Integration

  • Backlog Refinement: The spec is drafted during refinement. A story is "ready" when the spec passes a readability test — can another engineer implement it without asking clarifying questions?
  • Definition of Ready: Add a line: "The item has an EARS-formatted spec approved by the product owner and a technical reviewer."
  • Sprint Planning: Estimate based on spec complexity — number of EARS clauses, edge cases, cross-service touchpoints — not gut feel.
  • During the Sprint: The approved spec is frozen. Changes go through a mini Phase 1: draft amendment, review, approve.
  • Retrospective: Ask: "Where did the spec diverge from implementation, and why?"

Kanban Integration

  • Upstream queue: Add a "Spec Needed" column. Cards cannot enter "Ready for Dev" without a locked spec, plan, and tasks.
  • WIP limits: Apply a WIP limit to "Spec Needed" – typically 2× your dev WIP limit to avoid spec inventory waste.
  • Pull criteria: All EARS clauses have corresponding acceptance criteria; plan reviewed; tasks sized to fit average cycle time; no open clarification questions.

Spec Versioning & Lifecycle

  • Archive on merge: Move spec to archive/ when the feature ships.
  • Amend, do not overwrite: Create spec-v2.md for changes to preserve audit trail.
  • Delete after 90 days: If a spec hasn't been referenced, delete it — git history preserves it.
  • Living specs for living features: Actively maintained features keep specs in the active folder, updated with code changes.

CI/CD Integration

  • PR checklist from tasks.md: Auto-generate a checklist from tasks.md.
  • EARS lint in CI: Regex check that every spec contains "shall" and no banned words ("should", "may").
  • Spec-required gate: GitHub Action fails if a PR touches src/ without a corresponding spec.
  • Plan.md as PR comment: Paste plan summary into PR description.

The 5-Point Scorecard

The 4-phase loop tells you how to run agentic work. It does not tell you whether what came out the other end was actually good. That is a separate question — and it is the one Andrej Karpathy's "agentic engineering" framework is really about: the discipline of judging agent output, not just producing it. Score every spec-driven task against these five dimensions before you approve the merge.

Two-Stage Review

Stage 1 — Spec compliance: Does the diff implement what plan.md and tasks.md describe? Ignore code quality, style, and efficiency for this pass.

Stage 2 — Code quality: Now check security, test coverage, style consistency, and elegance. Do not let the quality review distract you from catching a stage 1 mismatch. If the code is beautiful but solves the wrong problem, it is still a failure.

This separation is the single most effective habit for preventing "the agent did something impressive but unrelated to what I asked for."

4. Security oversight — check identity, auth, trust-boundary logic against Constitution.
5. Taste — grep for existing patterns this diff could have reused.

# Report scores only. Do not approve the merge — that stays a human decision.

# --- Tool-specific save locations ---
# Claude Code: .claude/commands/scorecard.md
# Kiro CLI: run in a second terminal / separate Kiro context
Why This Matters

Every one of these five failure modes looks identical on the surface: code that compiles, passes tests, and "works." That is exactly why a scorecard beats a gut check — the risk in agentic engineering is not broken code, it is code that quietly ships debt, security gaps, or architectural drift that only surfaces months later.

When the Loop Breaks

The 4-phase loop assumes a happy path. Production teams hit these failure modes weekly. Here is how to recover when the agent stalls, the spec contradicts itself, or the plan turns out to be impossible.

Failure: Agent Stuck in Phase 4 (Infinite Retry)

Symptom: The agent runs the same failing test 10+ times, tweaking the code slightly each time but never fixing the root cause.

Root cause: The task in tasks.md is too large or the definition of done is vague.

Recovery: Stop the agent, read the failing test and last diffs, split the task into two smaller tasks (one to reproduce, one to fix), update tasks.md, and restart.

Failure: Spec Contradicts Itself

Symptom: R3 says "return 401" and R7 says "return 403" for the same condition.

Recovery: Do not let the agent guess. Update spec.md to resolve the conflict explicitly, re-run Plan, then re-run affected tasks.

Failure: Plan is Technically Infeasible

Symptom: The plan proposes a banned library or violates schema constraints.

Recovery: Reject the plan immediately, add the constraint to the Constitution, regenerate the plan with the constraint explicit.

Failure: Diff is Correct, But the Spec Was Wrong

Symptom: Implementation matches spec, but spec described the wrong behavior.

Recovery: Update spec.md first, re-run affected phases. Never patch code and leave spec stale.

Recovery decision tree: fix the spec first, then the code
The Golden Rule of Recovery

When in doubt, fix the spec first. Patching the code and leaving the spec stale creates the exact drift SDD was designed to prevent.

SDD vs. TDD vs. BDD

SDD gets confused with test-driven and behavior-driven development constantly, because all three share the same instinct: define correctness before you write the implementation. The difference is what document is treated as the canonical, load-bearing artifact.

ApproachCanonical artifactCore questionWhere tests come from
TDDThe test file"Write the failing test first."Tests come first; implementation follows to satisfy them.
BDDThe Gherkin scenario"Describe behavior in business language first."Scenarios written collaboratively with stakeholders, then automated.
SDDThe full specification"Write intent, architecture, edge cases, and constraints — then let the agent produce code, tests, and docs."Generated from the spec, not written ahead of it by a human. The Test Plan section in spec.md defines the tests before the agent writes a single line of implementation.

How They Work Together

  • Integration tests — generated by the agent from the spec's Test Plan and acceptance criteria. You review them, you do not write them.
  • Unit tests — written by you. The spec is too coarse-grained to dictate every branch condition. Your TDD discipline still applies here.
  • EARS requirements — written collaboratively (you + agent). They are the contract both sides agree to before code is written.
Practical Test

If your team already does TDD, add one line to your process: "No red test without a corresponding EARS requirement in the spec." The spec becomes your source of testable requirements, and TDD becomes the mechanism for proving the implementation satisfies them.

Superpowers: The Cross‑Tool Methodology Layer

Superpowers (obra/superpowers) is an open-source skills framework that layers a full SDD methodology on top of many agents — Claude Code, Cursor, Codex, Gemini CLI, Kimi Code, and more. It is not a replacement for Kiro or Claude; it is a harness layer that enforces a disciplined workflow regardless of which agent you use.

Superpowers enforces these mandatory workflows:

  • Brainstorming — structured exploration of the problem space before spec writing.
  • Design validation — check the plan against the Constitution and existing codebase.
  • Git worktree isolation — every task runs in a clean, isolated workspace.
  • Bite-sized plans — tasks are capped at 2–5 minutes.
  • Subagent-driven execution — separate agents for planning and implementation.
  • Two-stage review — spec compliance first, then code quality.
  • TDD discipline — tests before code, enforced at the workflow level.
  • Branch cleanup — automated cleanup of worktrees and branches after merge.
When to Evaluate Superpowers

If your team uses multiple agents and you want a single spec discipline that works across all of them, Superpowers is worth a look. It also validates that SDD principles are tool-agnostic — the methodology is the product, not the CLI.

First Project Tip

Run your first pass on something small and real — a rate limiter, a webhook validator, a single CRUD endpoint. Learn the rhythm of the workflow before you trust it on anything with production stakes.

The Build-Test-Harden Sequence

  1. Build the loop first. Run one complete 4-phase cycle on a small, real feature.
  2. Build the harness next. Add your Constitution, steering files, and the 5-point scorecard.
  3. Harden both together. Add CI gates, spec versioning, and the verifier pattern. Track scorecard metrics over time.

Teams that try to implement the full harness before they understand the loop usually over-engineer the constraints and under-engineer the workflow. Build, then test, then harden.

Annotated Example: Token-Bucket Rate Limiter

This is the complete spec for the rate limiter mentioned in Sheet 04. Every section is annotated to explain why it is written this way. Copy the structure, adapt the content.

requirements.md

specs/rate-limiter/requirements.md
# Rate Limiter Middleware

## Background
Prevents abuse of public API endpoints. Deployed as Express middleware.

## EARS Requirements
When a request is received, the system shall count that request against the client's token bucket.
If the bucket is empty, the system shall return 429 with Retry-After.
If the request has no valid API key, the system shall return 401 before evaluating the rate limit.
While the server is running, the system shall refill each bucket at 100 tokens/sec up to 150 burst.

## Non-goals
No per-IP rate limiting (handled by WAF). No admin dashboard. No distributed rate limiting.

## Assumptions
In-memory storage is sufficient for single-node deployment. API keys validated upstream. Monotonic time used for refills.

## Constraints
Must use existing lib/rate-limiter.ts utility. No new external dependencies.

## Reference implementation
See _spec/spikes/reference/token-bucket-spike/ for a working prototype.

## Test Plan
T1: 100 requests in 1 second → all return 200.
T2: 101st request → returns 429 with Retry-After ≥ 1.
T3: Invalid API key → returns 401, no token consumed.
T4: After 1 second of no requests → next request returns 200.
T5: Load test: 10,000 requests over 10 seconds → no memory leak, all within 200ms.

## Acceptance Criteria
AC1–AC4 as described. All existing integration tests continue to pass.

## Out of Scope
Per-IP rate limiting, admin dashboard, distributed rate limiting.

design.md

specs/rate-limiter/design.md
# Rate Limiter — Technical Design

## Architecture Decision
Use token-bucket algorithm with floating-point token count and last-refill timestamp stored in an in-memory Map keyed by API-key ID.

## Data Flow
1. Request arrives → middleware extracts API key from Authorization header.
2. If key invalid → return 401.
3. If key valid → look up bucket in Map. If missing, create with 150 tokens.
4. Calculate elapsed time, add tokens at 100/sec.
5. If tokens ≥ 1 → decrement and call next().
6. If tokens < 1 → return 429 with Retry-After = ceil(1 / refillRate).

## Component Design
src/middleware/rate-limiter.ts (new), src/lib/token-bucket.ts (new), import existing lib/rate-limiter.ts.

## Dependencies
None — uses native Node.js process.hrtime.bigint().

## Risk Assessment
Memory leak: periodic sweep of stale entries older than 1 hour. Clock skew: hrtime is monotonic. Horizontal scaling: out of scope for this iteration.

tasks.md

specs/rate-limiter/tasks.md
# Rate Limiter — Implementation Tasks

## T01: Implement token-bucket math
Create src/lib/token-bucket.ts with Bucket class. Unit tests pass.
Verification: npm test -- token-bucket  Effort: S (3 min)

## T02: Implement middleware
Create src/middleware/rate-limiter.ts, integrate with existing utility.
Definition of done: middleware extracts key, checks bucket, returns correct status.
Verification: npm test -- middleware  Effort: M (4 min)  Depends: T01

## T03: Add integration tests
Test AC1–AC4 and T1–T5 from Test Plan.
Verification: npm run test:integration  Effort: M (5 min)  Depends: T02

## T04: Add memory pruning
Periodic sweep of stale Map entries. Load test passes.
Verification: npm run test:load  Effort: S (2 min)  Depends: T01

Why This Structure Works

  • requirements.md contains only behavior — no implementation hints. The Non-goals, Assumptions, and Reference implementation sections prevent the agent from re-deciding choices you have already made.
  • design.md contains the algorithm choice and risk assessment. If the diff shows a different algorithm, the reviewer catches it immediately.
  • tasks.md maps 1:1 to acceptance criteria and the Test Plan. Each task has an estimated time that enforces the 2–5 minute granularity rule.
Use This as Your Template

Save these three files as templates/spec/ in your repo. For every new feature, copy the folder, rename it, and fill in the blanks. The structure is the product; the content is the project.

Acronyms & Glossary

Navigating the SDD ecosystem means decoding a dense alphabet soup of terms. Here is a curated list of the most important acronyms and their meanings in the context of Spec-Driven Development.

AcronymFull FormContext / Meaning
SDDSpec-Driven DevelopmentThe core methodology where the specification is the single source of truth, and code is a generated artifact.
TDDTest-Driven DevelopmentA development process where you write a failing test first, then write just enough code to pass it.
BDDBehavior-Driven DevelopmentAn extension of TDD using shared language (Gherkin) to define behavior, often written as Given-When-Then.
EARSEasy Approach to Requirements SyntaxA structured notation (When/While/If/Where) for writing precise, testable requirements, heavily used in Kiro.
DoRDefinition of ReadyThe entry-quality criteria a story must meet before being pulled into a Scrum sprint — the natural anchor point for a maturing spec.
BDUFBig Design Up FrontA complete design agreed upon before implementation starts and defended by phase gates — the waterfall pattern SDD gets mistakenly conflated with when the spec is frozen rather than living.
WIP limitWork-in-Progress LimitA cap on the number of tasks allowed at a given Kanban stage, used in Upstream Kanban to prevent overproducing specs that go stale.
IDEIntegrated Development EnvironmentSoftware like VS Code, Cursor, or Kiro that provides comprehensive facilities to programmers.
CLICommand Line InterfaceA text-based interface used to run tools like Kiro CLI or Claude Code.
LLMLarge Language ModelThe AI model (e.g., Claude, GPT, Gemini) that interprets the spec and generates code.

Understanding these terms is essential for reading tool documentation and contributing to team discussions around SDD adoption.
