What is Spec-Driven Development?

Spec-Driven Development (SDD) is the structural successor to "vibe coding" — the term Andrej Karpathy coined in February 2025 for the ad-hoc, prompt-and-pray loop of throwing natural-language instructions at a model until something works. By mid-2026 it had become clear that vibe coding does not hold up once real users, real security requirements, and real teammates are in the loop.

SDD is a methodology in which a written specification is treated as the primary, executable artifact of a software project, and code is a regenerable output produced from that spec by humans, AI agents, or both. The specification file, not the eventual codebase, becomes the single source of truth. Instead of describing a system brick-by-brick through an endless chat, you hand an autonomous agent a complete engineering blueprint. It builds against that blueprint, and when requirements change, you edit the spec and regenerate the code rather than hand-patch the output.

As Birgitta Böckeler of Thoughtworks puts it, SDD fundamentally means that "the specification is the single source of truth, and the code is a generated artifact." This shifts the developer's role from writing every line of code to maintaining the authoritative document that defines what the system should do.

The problem it actually solves

Improvising via chat is great for a prototype and dangerous for anything that has to survive contact with production. Models are extraordinary pattern-completers and unreliable mind-readers. Left unconstrained, ambiguity in your intent does not stay small — it compounds into architectures nobody chose on purpose, missing security controls, unhandled edge cases, and thin-to-nonexistent test coverage. Teams have taken to calling this failure mode "automating the creation of legacy mess." A written spec turns fuzzy intent into a deterministic contract the agent cannot quietly drift away from. The lever for output quality shifts from prompt cleverness to spec quality.

The Continuum of Commitment

Rolling SDD into a real engineering team is not binary — it sits on a spectrum of how much authority you are willing to hand the spec. Most teams start at level one and drift toward level two; very few production shops run level three today. As Thoughtworks' Birgitta Böckeler notes, "all SDD approaches and definitions I've found are spec-first, but not all strive to be spec-anchored or spec-as-source."

LEVEL 1

Spec-First

A well-thought-out spec is fully drafted before engineering starts. The agent writes the baseline; from there, the human developer reviews, edits, and maintains the code by hand. Highest risk of the spec going stale the moment the first hotfix lands.

LEVEL 2

Spec-Anchored

Specs are treated as living, long-term artifacts that evolve alongside new features. Humans actively keep code and spec synchronized, so both remain aligned through the entire maintenance lifecycle — not just at launch.

LEVEL 3

Spec-As-Source

The specification is the only file humans edit. Generated code carries markers like // GENERATED FROM SPEC — DO NOT EDIT. Application code is treated as a compiled, transient byproduct — closer to how a build treats a .class file than how a team treats a repo.

Watch For

Level 3 is the one vendors talk about most and teams actually run least. Treat it as a destination worth understanding, not a default starting point — most production teams get the bulk of SDD's value by simply reaching Level 2 and staying there.

Does Vibe Coding Disappear?

No — it moves, it does not vanish. At Spec-First, ad-hoc prompting is completely normal after the initial build; the spec did its one job and steps aside. At Spec-Anchored, it is still normal for anything that does not change what the system does — you just triage first. At Spec-As-Source, the loose, exploratory energy shifts into the spec text itself: you never hand-edit generated code, but iterating on the spec is still just as conversational as vibe coding always was.

Core Workflow: The 4-Phase Loop

The SDD loop is a collaboration between you (the human) and the AI agent. Each phase has a clear division of labour: the agent drafts, you review and approve. Here is exactly who does what.

PhaseWhat the AI Agent doesWhat You (the Human) doesHandoff / Checkpoint
1. Specify Drafts the initial spec, asks clarifying questions, flags gaps Writes the initial description, reviews the drafted spec, answers questions, approves it You say "yes, proceed" — spec is locked
2. Plan Reads the spec, generates a technical architecture plan Reviews the plan, checks feasibility, approves or requests changes You say "yes, proceed" — plan is locked
3. Tasks Breaks the plan into an ordered checklist of micro-tasks Reviews the task list, checks completeness, approves it You say "yes, proceed" — task list is locked
4. Implement Executes the tasks one by one, writes code, runs tests Reviews the targeted diffs, validates against the spec, approves the merge You review each change; agent loops back if you request fixes
The Golden Rule

The agent never moves to the next phase without your explicit approval. You are the decision-maker. The agent is the executor. This is what prevents the "automated legacy mess" problem — you stay in control.

Greenfield vs. Brownfield: Where Phase 1 Actually Starts

The four phases are the same either way, but Phase 1 starts from a different place. Greenfield — there is no existing code to contradict, so the spec you write is genuinely the first source of truth. Brownfield — the codebase already has an implicit spec: however it actually behaves today, documented or not. Skip acknowledging that, and Phase 1 will happily draft requirements that quietly conflict with what is already shipped. Both tools have a specific fix for this — see Sheet 09 for the exact commands.

Phase 1 — Specify & Clarify

What the AI Agent does:

  • Reads your initial description (a few sentences about what you want to build).
  • Drafts a structured spec.md with functional requirements, constraints, and success criteria.
  • Runs a clarification pass — it identifies logical gaps, contradictions, and ambiguous statements.
  • Asks you specific questions to fill in the blanks ("What should happen if the API key is invalid?", "How many requests per second do you expect?").
  • Updates the spec based on your answers.

What You (the Human) do:

  • Write the initial description — just a few sentences about what you need.
  • Read the draft spec the agent produces.
  • Answer the agent's clarification questions.
  • Review the final spec and explicitly approve it before the agent moves to Phase 2.
Example Conversation

You: "Build a token-bucket API rate limiter middleware."
Agent: "I'll draft a spec. How many requests per second? What should the response be when rate-limited?"
You: "100 per second. Return 429 Too Many Requests."
Agent: "Here's the complete spec. Does this cover everything?"
You: "Yes, proceed." → Phase 1 complete.

Phase 2 — Plan

What the AI Agent does:

  • Parses the approved spec and generates a technical plan.md.
  • Decides on state management, dependency choices, data serialization formats, service-to-service communication, component and schema design.
  • Runs a risk assessment — flags security liabilities and integration pain points.
  • Produces a detailed architecture document that maps each requirement to a concrete implementation strategy.

What You (the Human) do:

  • Read the plan.md the agent generates.
  • Check if the technical approach makes sense for your context.
  • Flag any concerns or request changes.
  • Explicitly approve the plan before the agent moves to Phase 3.

Phase 3 — Tasks

What the AI Agent does:

  • Breaks the plan into an ordered checklist of micro‑tasks in tasks.md.
  • Each task is small and isolated enough to implement sequentially without collisions.
  • Each task includes its own definition of done and inline verification instructions.
  • Tasks map directly to the acceptance criteria from Phase 1.

What You (the Human) do:

  • Review the tasks.md checklist.
  • Check that all acceptance criteria are covered and the order makes sense.
  • Add or remove tasks if needed.
  • Explicitly approve the task list before the agent starts writing code.

Phase 4 — Implement

What the AI Agent does:

  • Executes the tasks one by one, in order.
  • For each task, it writes code — but not as a giant dump. It produces targeted diffs — small, focused changes.
  • Runs tests and linters against its own changes.
  • Continuously checks its work back against the Phase 1 spec. If it hits ambiguity, it re‑queries you.
  • If a task fails verification, it attempts to fix it or flags it for you.

What You (the Human) do:

  • Review each targeted diff — small changes are easier to understand and validate.
  • Test the code locally or in your staging environment.
  • If a change does not match the spec, reject it and the agent re‑works it.
  • Once all tasks are done and verified, approve the final merge.
The Verifier Pattern

The most underused refinement: assign a separate agent to verify the implementing agent's work rather than trusting it to self‑check. Treat "verifier" as a distinct role in your pipeline — the same way you would not let one engineer be the only reviewer of their own pull request. See Sheet 07 for a reusable reviewer prompt you can save as a command.

How This Plays Out in Practice

Kiro CLI: The built‑in /spec agent automates this entire loop. You run /spec new, the agent produces requirements.md. You review and type "proceed" — agent moves to design.md. You review and type "proceed" — agent moves to tasks.md. You review and type "proceed" — agent runs /spec run and executes the tasks, showing you each diff as it goes.

Claude Code: You bring your own workflow. Real plugins and custom commands give you structured steps for requirements, planning, and execution where each phase requires your explicit approval before moving to the next. See Sheet 09 for tool-specific setup.

Writing Specs with EARS

EARS — the Easy Approach to Requirements Syntax — is the bridge between human intent and machine execution. It forces ambiguity out of requirements by replacing prose with structured clauses an LLM can parse as cleanly as a compiler parses code.

Developed by Alistair Mavin and adopted by aerospace and automotive engineering, EARS has five keywords that cover virtually every functional requirement you will write: When, While, Where, If, and Shall. The syntax is deliberately rigid because rigidity is exactly what prevents an agent from hallucinating intent.

When

Event-Driven Requirements

Use When for discrete triggers. "When the user clicks Submit, the system shall validate the payload." The event is singular and unambiguous.

While

State-Driven Requirements

Use While for continuous conditions. "While the connection is open, the system shall heartbeat every 30 seconds." Describes sustained behavior, not a one-off.

If

Conditional Requirements

Use If for branching logic. "If the API key is invalid, then the system shall return 401 before evaluating the rate limit." Nests inside When or While.

Where

Contextual Requirements

Use Where for scoped behavior. "Where the request originates from an internal subnet, the system shall bypass the rate limiter." Sets boundaries.

Why EARS matters for SDD

Large language models are pattern-completers. When you feed them structured patterns, they complete the right pattern. When you feed them vague prose, they complete whatever pattern is statistically nearest — which may not be what you meant. EARS gives the agent a grammar to follow, not just a topic to riff on.

As a practical rule: if you cannot restate a requirement as a When/If/While/Where clause followed by "the system shall," the requirement is not ready for an agent. It still has ambiguity that will compound into architectural drift.

From Vague to Verifiable

Vague (what not to write)EARS-compliant (what to write)
"The API should handle rate limiting." "When a client exceeds 100 requests in a 1-second window, the system shall return HTTP 429 and include a Retry-After header."
"Users must be authenticated." "When a request is received without a valid JWT, the system shall return 401 and shall not process the payload."
"The system should be fast." "When the database query returns more than 10,000 rows, the system shall paginate the response and shall return the first page within 200ms."
"Log errors properly." "If an unhandled exception occurs, the system shall write the stack trace to stderr with a UTC timestamp and shall return 500 to the client without exposing internal paths."

Common EARS Anti-Patterns

  • "Shall be able to" — This describes capability, not obligation. The agent may implement the feature as optional. Use "shall" alone for mandatory behavior.
  • "Shall consider" — Unverifiable. How do you test whether something was "considered"? Replace with a concrete action.
  • Multiple requirements in one sentence — "When X happens the system shall do Y and Z and also notify Q." Split into atomic sentences. One clause, one obligation.
  • Missing the trigger — A requirement that starts with "The system shall..." but never says When or If leaves the agent guessing about invocation context.

Nested Conditions

Real requirements rarely fit a single keyword. EARS supports nesting:

Nested EARS example
# Good: nested, unambiguous
When a payment request is received,
  If the account balance is sufficient,
    the system shall debit the amount and shall return 200.
  If the account balance is insufficient,
    the system shall return 402 and shall log the attempt.

# Bad: ambiguous ordering and missing branch
The system should process payments and handle errors.
Quick Reference

Before you approve any spec.md, run the EARS lint: can every requirement be prefixed with When/While/If/Where and end with a single "shall" action? If not, send it back for rewriting. This one habit prevents more agentic drift than any prompt-engineering trick.

Spec in Scrum & Kanban

A spec that lives outside your delivery rhythm is a spec that dies. SDD does not replace Agile — it needs to be wired into your existing ceremonies and board states. The goal is not more documentation; it is the right documentation at the right time.

Scrum Integration

In Scrum, the spec is the bridge between product intent and sprint execution. It should be treated as a first-class artifact, not an afterthought attached to a Jira ticket.

Backlog Refinement

  • Stories entering refinement must have a draft spec — even if rough. Refining without a spec is guessing at scope.
  • The team reviews the spec for EARS completeness, not just story points. If a requirement cannot be written in EARS, the story is not ready for estimation.

Definition of Ready (DoR)

Add spec completeness as a DoR gate. A story is not ready to be pulled into a sprint until:

  • The spec.md is drafted and reviewed by at least one engineer.
  • All EARS requirements have acceptance criteria that map 1:1 to testable outcomes.
  • Security and performance constraints are explicitly stated (not implied).

Sprint Planning

  • Review the spec, not just the story title. The spec is the sprint contract.
  • The agent (or team) generates plan.md and tasks.md during or immediately after planning.
  • Capacity planning should account for human review time — each phase gate needs a reviewer.

During the Sprint

  • The spec is living. If implementation reveals a constraint that invalidates part of the spec, update the spec first, then the code.
  • Daily standup status: "Task 3 of 7 complete, spec updated to reflect the new auth flow."

Sprint Retrospective

  • Did the spec match what we built? If not, why — ambiguous EARS clauses, missed edge cases, or scope creep?
  • Track spec drift: how many tasks required out-of-band clarifications because the spec was incomplete?

Kanban Integration

Kanban's flow-based model maps naturally to SDD if you treat specs as work items with their own WIP limits.

Kanban flow with dedicated spec stages and WIP limits

Upstream Kanban: The Spec Queue

  • Create an upstream section on your board: "Spec Needed" and "Spec Review" columns before "Ready for Dev."
  • Apply WIP limits to spec stages. If you allow infinite specs in flight, you create inventory waste — specs that go stale before implementation.
  • Pull criteria for "Ready for Dev": EARS-complete, reviewed by engineer, security constraints stated, acceptance criteria mapped.

Avoiding Spec Inventory Waste

A spec written three months before implementation is a spec written for a codebase that no longer exists. The rule: spec at most one to two sprints ahead. Any further and you are doing Big Design Up Front (BDUF) with extra Markdown. If priorities shift, archive the spec rather than letting it rot in the queue.

The BDUF Trap

SDD is compatible with Agile when specs stay lightweight and living. The moment they calcify into Waterfall-style documentation written quarters ahead of code, you have lost the point. The Thoughtworks Technology Radar specifically flags this risk: SDD can tilt back toward big up-front specification if teams are not disciplined about just-in-time refinement.

Practical Heuristic

If a spec has not been pulled into implementation within two sprints of being written, archive it. The world — and your codebase — will have changed enough that resurrecting it costs more than rewriting it.

The Constitution & Standing Context

Every project needs two kinds of document: temporary specs that exist for one feature, and standing rules that apply to every change. The Constitution is your immutable foundation — the second kind.

As Birgitta Böckeler of Thoughtworks puts it: "general context are things like rules files, or high level descriptions of the product and the codebase… whereas specs [are] only relevant to the tasks that actually create or change that particular functionality." That standing-rules document is what this section covers.

What the Constitution Covers

A Constitution defines non‑negotiable principles that apply to every change — testing philosophy, security baselines, code style, and opinionated technology choices. This ensures organizational standards are baked into every project from the start.

constitution.md (generic template)
# Project Constitution — immutable principles
- All database mutations must use explicit transaction boundaries.
- All public endpoints must include active rate-limiting middleware.
- Unit tests are required for any newly created utility method.
- Write tests before implementing any business logic (TDD discipline).
- No raw SQL in controllers — all queries go through the repository layer.
- Secrets must be injected via environment variables, never hard-coded.

How the Constitution Fits into the Loop

  • You write it once at the start of the project.
  • The agent reads it at the beginning of every session — it is part of its permanent memory.
  • Every phase respects the Constitution: the agent will not propose a plan that violates it, and you use it as your own checklist during reviews.

Implementation by Tool

Kiro CLI — Steering Files

Store your Constitution in steering files inside .kiro/steering/. For example, put architecture rules in tech.md, structural rules in structure.md, and product rules in product.md. Since steering files are always loaded in every interaction, they automatically enforce your immutable rules on every change — no extra configuration needed.

.kiro/steering/tech.md — Kiro's Constitution
# Technology Constitution
- All database mutations must use explicit transaction boundaries.
- All public endpoints must include rate-limiting middleware.
- Write tests before implementing any business logic.
- All external API calls must have a 5-second timeout and circuit-breaker fallback.

Claude Code — CLAUDE.md

Place your Constitution directly in CLAUDE.md, which is read at the start of every session. For larger rulebooks, keep a separate constitution.md and reference it in CLAUDE.md using the @constitution.md syntax. This ensures Claude applies your rules to every task it touches.

CLAUDE.md — Claude's Constitution
# Project Constitution (loaded every session)
- All database mutations must use explicit transaction boundaries.
- All public endpoints must include rate-limiting middleware.
- Write tests before implementing any business logic.

# Reference a separate constitution file if it grows large
@constitution.md

Brownfield Bootstrapping

Both tools can generate a starter Constitution from an existing codebase instead of writing it blank:

  • Kiro: Use Generate Steering Docs (IDE button, CLI, or Web) to scan the repo and auto-draft product.md, tech.md, and structure.md from what is actually there.
  • Claude Code: Run /init in the repo before writing anything by hand — it detects your build system, test framework, and code patterns, and drafts a starter CLAUDE.md you refine from there.

Either way, do this before your first spec, not after — it is what stops Phase 1 from drafting requirements that quietly contradict how the codebase already works.

Constitution = Persistent Context

Whether you use Kiro's steering files or Claude's CLAUDE.md, the Constitution is your team's living rulebook. It outlasts any single feature spec and ensures every AI session starts with the same non‑negotiable standards. Update it rarely — treat it like a real constitution, not a daily checklist.

The 5-Point Scorecard

The 4-phase loop tells you how to run agentic work. It does not tell you whether what came out the other end was actually good. That is a separate question — and it is the one Andrej Karpathy's "agentic engineering" framework is really about: the discipline of judging agent output, not just producing it. Score every spec-driven task against these five dimensions before you approve the merge.

DimensionWhat you are checkingKiro CLIClaude Code
Spec design Were invariants and security boundaries written down before prompting — not just a loose description? EARS-formatted requirements.md, reviewed and approved before "proceed" Feature spec via custom or plugin-based specification commands, approved before Plan
Diff review Was the diff checked against architecture and the approved plan — not just "tests pass"? Review each diff as /spec run executes tasks sequentially against design.md Review targeted diffs per task against the approved plan; use a separate reviewer sub-agent for pattern violations
Eval design Is there an objective, repeatable score — not a vibe check — proving the output is good? Task-level "definition of done" + inline verification instructions per tasks.md entry Custom eval scripts / CI gates tied to acceptance criteria in task logs
Security oversight Was every identity-, auth-, or cross-system decision reviewed for plausible-but-wrong assumptions? Enforced via always-loaded .kiro/steering/tech.md rules (the Constitution) Enforced via CLAUDE.md Constitution rules, reviewed on a separate security pass
Taste Does the code reuse existing patterns and stay lean, or default to a generic, bloated solution? Verifier agent pattern — a distinct agent checks output after /spec run, not the implementer itself Dedicated reviewer sub-agent with its own context, separate from the implementing agent

Scorecard in Action: One Feature, Five Checks

The table above tells you what to check. What actually makes it click is seeing a real red flag next to the fix that catches it. Take the token-bucket rate limiter from Sheet 03's Phase 1 example and run it through all five dimensions — this is the level of concreteness you are aiming for in your own reviews, not a vague "looks fine."

DimensionRed flag (what actually goes wrong)Green flag (what good looks like)How you catch it
Spec design requirements.md just says "add rate limiting to the API" — no trigger, no boundary, no error format. "When a client exceeds 100 requests in a 1-second window, the system shall respond with 429 and a Retry-After header. If the request has no valid API key, then the system shall return 401 before evaluating the rate limit." Both the happy path and the auth-ordering edge case are explicit. Kiro: before typing "proceed," try restating each requirement as a When/If clause — if you cannot, it is not ready. Claude Code: same test, applied before approving Plan.
Diff review plan.md specifies a token bucket that refills continuously, but the diff implements a fixed window counter that resets every second — a quietly different, weaker algorithm that still passes the same tests. The diff contains a bucket struct with a token count and a last-refill timestamp — matching plan.md's stated approach line for line, not just its outcome. Kiro: as /spec run shows each diff, hold it next to design.md's algorithm section — not just "tests green." Claude Code: ask a reviewer sub-agent "does this diff implement what plan.md Section 3 describes, or a different approach that happens to pass the same tests?"
Eval design tasks.md says "add tests for rate limiter" — vague, so the agent writes one happy-path test and stops. The task's definition of done reads: "test: 101st request in a 1s window returns 429 with Retry-After ≥ 1; test: request with an invalid key returns 401 without consuming a token." Each line maps 1:1 to an EARS requirement. Kiro: check that every tasks.md verification line names a specific input/output pair, not "add tests." Claude Code: a CI gate that fails the merge if a task's test file does not reference its acceptance-criterion ID.
Security oversight The agent keys the rate-limit counter on client IP alone — reasonable-looking, but it breaks the moment two users share a corporate NAT or mobile carrier proxy, and it is trivially spoofed via X-Forwarded-For. The counter is keyed on the authenticated client/API-key ID, with IP used only as a secondary abuse signal. Kiro: a rule in .kiro/steering/tech.md — "never key security or quota logic on IP address alone" — is loaded every session, so Plan should propose the key-ID approach unprompted; if it does not, that is the flag. Claude Code: the same rule in CLAUDE.md, plus a dedicated pass: "review this diff only for identity and trust-boundary assumptions, ignore style."
Taste The project already has lib/rate-limiter.ts, used by two other endpoints — the agent writes a second, subtly different implementation inline in the new middleware instead of importing it. The diff imports and extends the existing shared utility, or explicitly proposes replacing it with a stated reason. Kiro: the verifier agent is prompted specifically to grep for existing rate-limiting code before approving — duplication is an automatic flag. Claude Code: the reviewer sub-agent's prompt includes "search the codebase for existing implementations of this pattern before judging the diff done."

A Reusable Reviewer Prompt

The fastest way to apply this scorecard consistently — instead of re-explaining it in every review — is to save it once as a real command and run it on every task, not just the ones that feel risky.

.claude/commands/scorecard.md — Claude Code custom command
# /scorecard
# Review the diff for this task against spec.md, plan.md, and tasks.md.
# Score 1-5 on each, with one line of justification:

1. Spec design — does every branch in the diff trace back to an EARS requirement?
2. Diff review — does the implementation match plan.md's stated approach,
   not just pass the same tests a different approach would also pass?
3. Eval design — does each test map to a specific acceptance criterion,
   not just "happy path passes"?
4. Security oversight — search for identity, auth, or trust-boundary logic;
   check it against CLAUDE.md's security rules for plausible-but-wrong assumptions.
5. Taste — grep the codebase for existing patterns this diff could have
   reused instead of reinventing.

# Report scores only. Do not approve the merge — that stays a human decision.
Kiro CLI — running the verifier as a separate session
# Open a second terminal / separate Kiro context —
# the reviewer must not be the same session that implemented the diff.

kiro

Save It Once, Run It Every Merge

Treating the scorecard as a saved command instead of something you re-type from memory is what makes it stick as a habit rather than a one-off exercise. It also means every reviewer on the team — human or agent — is checking against the exact same five questions.

Why This Matters

Every one of these five failure modes looks identical on the surface: code that compiles, passes tests, and "works." That is exactly why a scorecard beats a gut check — the risk in agentic engineering is not broken code, it is code that quietly ships debt, security gaps, or architectural drift that only surfaces months later. A 5/5 on eval with a 1/5 on taste is still a liability, not a pass.

How to Use It

Score each merged task 1–5 on all five dimensions, not just "did it work." Flag anything scoring low on security oversight for mandatory senior re-review regardless of how clean the rest of the diff looks. Track scores over time per repo — a consistent low score on spec design usually means your steering files or CLAUDE.md are underspecified, not that the agent is unreliable.

SDD vs. TDD vs. BDD

SDD gets confused with test-driven and behavior-driven development constantly, because all three share the same instinct: define correctness before you write the implementation. The difference is what document is treated as the canonical, load-bearing artifact.

ApproachCanonical artifactCore questionWhere tests come from
TDDThe test file"Write the failing test first."Tests come first; implementation follows to satisfy them.
BDDThe Gherkin scenario"Describe behavior in business language first."Scenarios written collaboratively with stakeholders, then automated.
SDDThe full specification"Write intent, architecture, edge cases, and constraints — then let the agent produce code, tests, and docs."Generated from the spec, not written ahead of it by a human.

In practice, SDD subsumes a lot of what BDD was reaching for: EARS-style acceptance criteria are essentially Gherkin's stricter cousin, written so an LLM can parse them as cleanly as a person can. A healthy SDD workflow still produces real unit and integration tests — they just fall out of the spec rather than preceding it by convention.

Not everyone agrees SDD should go all the way to "code as byproduct," though. Some engineers hold a more conservative position: specs are a superior prompt, the way they were always meant to drive TDD, but the executable code — not the Markdown — remains the artifact you actually maintain long-term. That disagreement traces back to how far you are willing to travel down the maturity continuum in Sheet 02.

You switch to it when you want the agent to think through requirements and design before writing code, then execute an implementation plan with verification between each task. The /spec commands let you list, create, resume, and run specs. When you run /spec new, the agent asks which type of spec you want — Build a Feature, Fix a Bug, or Quick Spec — and then produces the three files (requirements.md, design.md, tasks.md) with human review checkpoints between each phase. The specs are stored in .kiro/specs/, which is shared across all Kiro surfaces — start in the CLI, continue in the IDE.

Claude Code — bring your own SDD

Claude Code does not have a built‑in spec agent. Instead, you bring your own workflow through plugins, custom slash commands, hooks, and skills. You can set up structured loops (such as spec → plan → tasks → implement) using custom configurations or community packages that enforce human approval gates before moving to the next stage.

You can also build your own workflow using Claude Code's .claude/commands/ directory and skills. A popular pattern is a multi-phase approval process (Requirements → Design → Tasks → Implementation) where each phase requires human review and you cannot skip phases.

Claude Code extras: Skills & AGENTS.md

Beyond the spec workflow itself, Claude Code has two more building blocks worth knowing. AGENTS.md has become an open standard for giving any coding agent — not just Claude Code — durable project context, so it is worth using instead of a Claude-only file if you work across multiple agent tools. Claude Code Skills are shareable workspace macros stored in .claude/skills/ that encode team conventions — file structure, test patterns, accessibility rules — as on-demand commands Claude can invoke directly, giving you a way to package recurring, spec-adjacent knowledge (like "how we structure API routes") without stuffing it into CLAUDE.md itself.

Starting on an existing codebase (brownfield)

Both tools have a built-in way to bootstrap the Constitution from a codebase that already exists, instead of writing it blank. Kiro: use Generate Steering Docs (a button in the IDE, and the same capability in the CLI and Web) to scan the existing repo and auto-draft product.md, tech.md, and structure.md from what is actually there. Claude Code: run /init in the repo before writing anything by hand — it detects your build system, test framework, and code patterns, and drafts a starter CLAUDE.md you refine from there. Either way, do this before your first spec, not after — it is what stops Phase 1 from drafting requirements that quietly contradict how the codebase already works. See also Sheet 06 for Constitution details.

Picking One

If you want zero setup and an opinionated structure, start with Kiro CLI. If you already use Claude Code and want flexibility, start with custom commands or extensions. And if you want the best of both, start the spec in Kiro and implement it with Claude Code — the files are portable.

Vibe Coding vs. Spec-Driven: The Honest Call

SDD provides structural reliability, but it is genuine overhead for small tasks — turning a one-line fix into a web of user stories and acceptance criteria is its own anti-pattern, sometimes called "a sledgehammer to crack a nut."

Reach for Spec-Driven when:

  • You are writing production systems meant to scale and be maintained long-term.
  • Multiple engineers, or multiple parallel agents, work the same codebase at once.
  • You must enforce security profiles, data constraints, compliance rules, or design tokens precisely.
  • The system involves migrations, multi-service topologies, or intricate state machines.

Default to Vibe Coding when:

  • You are building throwaway code, isolated proofs-of-concept, or rapid wireframes.
  • The task is visual and needs fast, intuitive tweaking rather than a locked spec.
  • It is a minor bug fix — a full pipeline here is the sledgehammer problem above.
  • You are exploring an unfamiliar stack and do not yet know what you actually want.
A Practical Test

One heuristic experienced SDD practitioners use cuts through the ambiguity fast: if you would be annoyed to find the agent interpreted your requirement differently than you meant, write the spec. If a quick follow-up prompt would fix it just fine, skip the spec and prompt directly. It is a five-second gut check, and it is usually right.

Adoption Signals: Is This Actually Catching On?

SDD could easily be dismissed as another framework-of-the-month. Two things suggest otherwise: real production tooling has shipped around it (not just demos), and the industry-wide drop in developer trust toward unstructured AI-generated code is exactly the gap SDD's constraint layer is built to close.

Concrete case studies and field reports suggest teams are finding efficiency gains when matching specs to complex requirements, though exact timelines and savings vary by organization and project scope. Practitioners report that combining structured workflows with multi-agent execution helps streamline complex features.

On the tooling side, Kiro CLI brings spec-driven development to the terminal with a built‑in Spec agent. The Claude Code ecosystem has grown rapidly, with community extensions and custom workflows providing structured, spec‑first execution. The methodology has crossed from experimental to mainstream enough that educational platforms and industry courses have started featuring spec-driven development with coding agents.

Birgitta Böckeler's assessment captures the state of play: "Until I hear usage reports from people using them for a period of time on a 'real' codebase, I still have a lot of open questions about how this works in real life." The tools are evolving fast — they "might have already changed since I used them."

The Honest Limits

Every team adopting SDD should walk in aware of where it currently breaks down.

1. The brownfield adoption gap

SDD frameworks shine on greenfield projects where the agent builds from a clean slate. Dropping a full SDD pipeline onto a large legacy codebase in one go rarely works — it needs progressive, iterative adoption, feature by feature, not a big-bang rewrite. Both tools have a specific onboarding step for this (see Sheet 09), but even with it, treat the first few brownfield specs as trust-building exercises, not a reason to spec the entire legacy system at once.

2. The Markdown Monster risk

Adopt complex spec workflows without changing how your team actually collaborates, and you get documentation overhead instead of clarity. If a simple change spawns hundreds of verbose planning files, you are now spending more time reviewing prose than reviewing the code it produced. As Böckeler notes, "it is easy to end up with 100s of markdown files."

3. Semantic diffusion

As "spec-driven" gets popular, plenty of people use "spec" as a synonym for "a detailed prompt." That is not SDD — true SDD requires an execution engine that treats the specification as an actionable, verifiable source of truth, not just a longer prompt.

4. The heavy-upfront-planning critique

The Thoughtworks Technology Radar has placed SDD in its "Assess" ring — worth evaluating, not yet a default recommendation — and specifically flags a risk of the practice tilting back toward big up-front specification and big-bang releases, the same anti-pattern Agile spent two decades pushing teams away from. SDD is compatible with Agile when specs stay living, lightweight artifacts updated inside normal sprints — the moment they calcify into Waterfall-style documentation, you have lost the point.

5. The human-gates debate

There is a live disagreement about how much human review SDD pipelines should keep in the loop. One camp argues that as agents get faster and more capable, manual approval gates between phases become pure friction. The counter-argument, made forcefully by teams building for regulated environments: human gates were never there because agents cannot do the work — they exist because production software carries risk, compliance, and legal accountability that someone has to own, and an agent's growing ability to create value scales in lockstep with its ability to amplify a mistake. Where you land on this depends heavily on what you are building and who is liable if it is wrong.

Bottom Line

SDD is a genuine improvement over unstructured prompting for anything production-grade — but it is a discipline, not a silver bullet. It still requires someone to write a good spec, and a bad spec compiled perfectly is still a bad system.

Acronyms & Glossary

Navigating the SDD ecosystem means decoding a dense alphabet soup of terms. Here is a curated list of the most important acronyms and their meanings in the context of Spec-Driven Development.

AcronymFull FormContext / Meaning
SDDSpec-Driven DevelopmentThe core methodology where the specification is the single source of truth, and code is a generated artifact.
TDDTest-Driven DevelopmentA development process where you write a failing test first, then write just enough code to pass it.
BDDBehavior-Driven DevelopmentAn extension of TDD using shared language (Gherkin) to define behavior, often written as Given-When-Then.
EARSEasy Approach to Requirements SyntaxA structured notation (When/While/If/Where) for writing precise, testable requirements, heavily used in Kiro.
DoRDefinition of ReadyThe entry-quality criteria a story must meet before being pulled into a Scrum sprint — the natural anchor point for a maturing spec.
BDUFBig Design Up FrontA complete design agreed upon before implementation starts and defended by phase gates — the waterfall pattern SDD gets mistakenly conflated with when the spec is frozen rather than living.
WIP limitWork-in-Progress LimitA cap on the number of tasks allowed at a given Kanban stage, used in Upstream Kanban to prevent overproducing specs that go stale.
IDEIntegrated Development EnvironmentSoftware like VS Code, Cursor, or Kiro that provides comprehensive facilities to programmers.
CLICommand Line InterfaceA text-based interface used to run tools like Kiro CLI or Claude Code.
LLMLarge Language ModelThe AI model (e.g., Claude, GPT, Gemini) that interprets the spec and generates code.

Understanding these terms is essential for reading tool documentation and contributing to team discussions around SDD adoption.
