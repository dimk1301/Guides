What is Spec-Driven Development?

Spec-Driven Development (SDD) is the structural successor to "vibe coding" — the term Andrej Karpathy coined in February 2025 for the ad-hoc, prompt-and-pray loop of throwing natural-language instructions at a model until something works. By mid-2026 it had become clear that vibe coding does not hold up once real users, real security requirements, and real teammates are in the loop.

SDD is a methodology in which a written specification is treated as the primary, executable artifact of a software project, and code is a regenerable output produced from that spec by humans, AI agents, or both. The specification file, not the eventual codebase, becomes the single source of truth. Instead of describing a system brick-by-brick through an endless chat, you hand an autonomous agent a complete engineering blueprint. It builds against that blueprint, and when requirements change, you edit the spec and regenerate the code rather than hand-patch the output.

As Birgitta Böckeler of Thoughtworks puts it, SDD fundamentally means that "the specification is the single source of truth, and the code is a generated artifact." This shifts the developer's role from writing every line of code to maintaining the authoritative document that defines what the system should do.

The problem it actually solves

Improvising via chat is great for a prototype and dangerous for anything that has to survive contact with production. Models are extraordinary pattern-completers and unreliable mind-readers. Left unconstrained, ambiguity in your intent does not stay small — it compounds into architectures nobody chose on purpose, missing security controls, unhandled edge cases, and thin-to-nonexistent test coverage. Teams have taken to calling this failure mode "automating the creation of legacy mess." A written spec turns fuzzy intent into a deterministic contract the agent cannot quietly drift away from. The lever for output quality shifts from prompt cleverness to spec quality.

Loop Engineering vs. Harness Engineering

SDD sits at the intersection of two disciplines that teams constantly confuse. Loop engineering is the design of the iterative cycle that drives the agent toward a goal — your Specify → Plan → Tasks → Implement cycle. It governs what the agent does on each pass, how it evaluates progress, and when it stops. Harness engineering is the environment built around the agent — your Constitution, steering files, tool permissions, review gates, and recovery patterns. It governs what the agent is allowed to touch, how it recovers from failure, and how you observe what it did.

Confusing the two causes predictable failures. A weak harness lets an agent edit production configs because nobody said it could not. A weak loop makes agents brittle — they stall, retry forever, or stop too early because the exit condition is vague. SDD fixes both: the 4-phase loop is your loop, and the Constitution + scorecard is your harness. Naming the distinction gives you vocabulary to explain why SDD works to skeptical teammates.

The Continuum of Commitment

Rolling SDD into a real engineering team is not binary — it sits on a spectrum of how much authority you are willing to hand the spec. Most teams start at level one and drift toward level two; very few production shops run level three today. As Thoughtworks' Birgitta Böckeler notes, "all SDD approaches and definitions I've found are spec-first, but not all strive to be spec-anchored or spec-as-source."

LEVEL 1

Spec-First

A well-thought-out spec is fully drafted before engineering starts. The agent writes the baseline; from there, the human developer reviews, edits, and maintains the code by hand. Highest risk of the spec going stale the moment the first hotfix lands.

LEVEL 2

Spec-Anchored

Specs are treated as living, long-term artifacts that evolve alongside new features. Humans actively keep code and spec synchronized, so both remain aligned through the entire maintenance lifecycle — not just at launch.

LEVEL 3

Spec-As-Source

The specification is the only file humans edit. Generated code carries markers like // GENERATED FROM SPEC — DO NOT EDIT. Application code is treated as a compiled, transient byproduct — closer to how a build treats a .class file than how a team treats a repo.

Watch For

Level 3 is the one vendors talk about most and teams actually run least. Treat it as a destination worth understanding, not a default starting point — most production teams get the bulk of SDD's value by simply reaching Level 2 and staying there.

Core Workflow: The 4-Phase Loop

The SDD loop is a collaboration between you (the human) and the AI agent. Each phase has a clear division of labour: the agent drafts, you review and approve. Here is exactly who does what.

Structurally, this is an instance of the Plan-Execute-Verify (PEV) pattern — a three-phase harness architecture that separates planning from execution and enforces verification at every transition. Each phase in your loop is a PEV cycle: the agent plans (drafts), executes (produces), and you verify (review and approve) before the next cycle begins.

Pre-Phase 0: Spike the Unknowns New

If the feature contains technical uncertainty — a new API you have never integrated, an unproven performance path, an unfamiliar library with opaque behavior — run a throwaway spike before you write the spec. The spike is deliberately ugly: it is not meant to ship, it is meant to answer one question: "does this approach work?"

  • Keep it small. The spike should take less than two hours. If it takes longer, the uncertainty is too broad — split the problem.
  • Comment heavily. Mark every line that proves the approach works and every line that is intentionally incomplete (// PROVEN: this call returns the expected shape).
  • Store the reference. Save the spike in _spec/spikes/reference/<name>/ and link it from the spec's new Reference implementation section (see Sheet 04).
  • Bin or refactor. Once the spike proves the approach, either delete it or refactor the proven parts into the real implementation. Do not ship the spike as-is.

A working reference stops the agent from hallucinating behavior that "should" work but does not. It also gives you a concrete fallback when the agent's generated code fails: you can compare its approach against the reference and see exactly where it diverged.

When to Spike

Spike when you would say "I'm not sure if this will work" out loud. Do not spike for straightforward CRUD, known libraries, or patterns your team has already validated. The spike is a tool for uncertainty, not a replacement for reading documentation.

PhaseWhat the AI Agent doesWhat You (the Human) doesHandoff / Checkpoint
1. Specify Drafts the initial spec, asks clarifying questions, flags gaps Writes the initial description, reviews the drafted spec, answers questions, approves it You say "yes, proceed" — spec is locked
2. Plan Reads the spec, generates a technical architecture plan Reviews the plan, checks feasibility, approves or requests changes You say "yes, proceed" — plan is locked
3. Tasks Breaks the plan into an ordered checklist of micro-tasks Reviews the task list, checks completeness, approves it You say "yes, proceed" — task list is locked
4. Implement Executes the tasks one by one, writes code, runs tests Reviews the targeted diffs, validates against the spec, approves the merge You review each change; agent loops back if you request fixes
The Golden Rule

The agent never moves to the next phase without your explicit approval. You are the decision-maker. The agent is the executor. This is what prevents the "automated legacy mess" problem — you stay in control.

Phase 1 — Specify & Clarify (The Teaching Phase)

Phase 1 is where the loop earns its trust. The rest of the phases follow the same rhythm — draft, review, approve — but Phase 1 is where ambiguity is caught before it becomes architecture.

What the AI Agent does:

  • Reads your initial description (a few sentences about what you want to build).
  • Drafts a structured spec.md with functional requirements, constraints, and success criteria.
  • Runs a clarification pass — it identifies logical gaps, contradictions, and ambiguous statements.
  • Asks you specific questions to fill in the blanks ("What should happen if the API key is invalid?", "How many requests per second do you expect?").
  • Updates the spec based on your answers.

What You (the Human) do:

  • Write the initial description — just a few sentences about what you need.
  • Read the draft spec the agent produces.
  • Answer the agent's clarification questions.
  • Review the final spec and explicitly approve it before the agent moves to Phase 2.
Example Conversation

You: "Build a token-bucket API rate limiter middleware."
Agent: "I'll draft a spec. How many requests per second? What should the response be when rate-limited?"
You: "100 per second. Return 429 Too Many Requests."
Agent: "Here's the complete spec. Does this cover everything?"
You: "Yes, proceed." → Phase 1 complete.

Phases 2–4 — Same Rhythm, Different Artifacts

Once Phase 1 is locked, Phases 2–4 follow an identical pattern: the agent produces a draft, you review it against the prior phase's output, and you explicitly approve before the agent continues. The only difference is the artifact being produced.

PhaseAgent OutputYour Review Focus
2. Plan plan.md — architecture, dependencies, data flow, risk assessment Does the technical approach fit your stack? Are security liabilities flagged? Does it map every requirement to an implementation strategy?
3. Tasks tasks.md — ordered checklist of micro-tasks, each with definition of done and verification instructions Are all acceptance criteria covered? Is the order collision-free? Can each task be verified independently?
4. Implement Targeted diffs — small, focused code changes, one per task, with tests Does the diff match the plan? Does it reuse existing patterns? Does it satisfy the spec's EARS requirements?

Greenfield vs. Brownfield: Where Phase 1 Actually Starts

The four phases are the same either way, but Phase 1 starts from a different place. Greenfield — there is no existing code to contradict, so the spec you write is genuinely the first source of truth. Brownfield — the codebase already has an implicit spec: however it actually behaves today, documented or not. Skip acknowledging that, and Phase 1 will happily draft requirements that quietly conflict with what is already shipped. Both tools have a specific fix for this — see Sheet 11 for the exact commands.

The Verifier Pattern

The most underused refinement: assign a separate agent to verify the implementing agent's work rather than trusting it to self‑check. Treat "verifier" as a distinct role in your pipeline — the same way you would not let one engineer be the only reviewer of their own pull request. See Sheet 08 for a reusable reviewer prompt.

How This Plays Out in Practice

Kiro CLI: The built‑in /spec agent automates this entire loop. You run /spec new, the agent produces requirements.md. You review and type "proceed" — agent moves to design.md. You review and type "proceed" — agent moves to tasks.md. You review and type "proceed" — agent runs /spec run and executes the tasks, showing you each diff as it goes.

Claude Code: You bring your own workflow. Real plugins and custom commands give you structured steps for requirements, planning, and execution where each phase requires your explicit approval before moving to the next. See Sheet 11 for tool-specific setup.

Token Economics Reality Check Updated

Multi-phase agentic workflows burn tokens. A full 4-phase loop with a large spec can consume 50k–150k tokens before a single line of code is written. For a 10-minute bug fix, that is overkill — use vibe coding. For a 2-week feature touching multiple services, it is cheap insurance against architectural drift. Let the scope of the work decide whether you pay the overhead.

Side benefit: A precise spec lets you drop to a lower-tier model for implementation and still get output quality comparable to a top-tier model running on a vague prompt. The spec carries the precision; the model just executes. If you are burning tokens on Sonnet or Opus for every implementation pass, try Haiku or a comparable lower-tier model once the spec is locked — you may save 60–80% on token costs without a noticeable drop in code quality.

File Anatomy & Templates

The 4-phase loop produces three files. Without a standard structure, every team invents its own format and fragments. Here are the mandatory sections for each file — copy these templates directly into your repo and fill them in.

spec.md / requirements.md Updated
The Feature Contract
  • Title — One-line description of the feature.
  • Background — Why this feature exists. Business context, user pain, or system gap.
  • EARS Requirements — Numbered list of When/While/If/Where + shall clauses. One obligation per sentence.
  • Non-goals New — What this system explicitly will not do. Prevents overengineering and scope creep by making the boundaries visible.
  • Assumptions New — Decisions already made that the model should not silently re-decide (e.g., "cursor-based pagination, not offset"; "PostgreSQL 15, not 14").
  • Constraints — Hard limits the agent cannot violate (performance budgets, banned dependencies, compliance rules).
  • Reference implementation New — Link to a spike or existing code that proves the approach works. See Pre-Phase 0 in Sheet 03.
  • Test Plan New — Named tests with exact inputs and expected outputs, written before the implementation plan. Example: Test T1: POST /api/bulk with 10,001 rows → returns 413 in < 200ms. This becomes the definition of done for the implementation phase.
  • Acceptance Criteria — Verifiable outcomes that prove the feature works. Map 1:1 to EARS requirements and Test Plan entries.
  • Out of Scope — Explicitly excluded functionality to prevent scope creep (broader than Non-goals; captures entire features not included).
plan.md / design.md
The Technical Blueprint
  • Architecture Decision — The chosen approach and why alternatives were rejected.
  • Data Flow — How data moves through the system for this feature. Diagram or bullet list.
  • Component Design — New files, modified files, and their responsibilities.
  • Dependencies — New libraries or services required, with justification.
  • Risk Assessment — Security liabilities, integration pain points, and mitigation strategies.
  • Test Strategy — Unit, integration, and edge-case coverage plan.
tasks.md Updated
The Execution Checklist
  • Task ID — Sequential number (T01, T02...) for traceability.
  • Description — One-sentence objective.
  • Definition of Done — Exact criteria that mark this task complete.
  • Verification Command — The test or lint command that proves this task works.
  • Effort — Rough sizing (S/M/L) to catch tasks that are too large.
  • Dependencies — Which tasks must finish before this one starts.

Granularity rule New: Each task should be completable in 2–5 minutes of focused work. If a task exceeds that, split it. The agent should never be asked to hold enough context for a 30-minute task in a single pass. A 2–5 minute task has a single file change, a single test addition, or a single refactor — not a sprawling multi-file rework.

Why These Sections Matter

Skipping a section does not just make the file shorter — it makes the agent guess. No Constraints section means the agent proposes whatever dependency is statistically nearest. No Out of Scope means the agent quietly implements adjacent features it thinks are "obvious." No Verification Command in tasks means the agent decides when it is "done" — which is usually too early. No Non-goals means the agent optimizes for features you never asked for. No Assumptions means the agent re-decides technical choices you already made, wasting tokens on re-architecture. No Test Plan means the agent writes tests that prove the code works but not that it solves the right problem.

Start With a Skeleton

Do not wait until you have perfect content to create the file. Create the skeleton with all headers first, then fill in the EARS requirements. The skeleton acts as a checklist: if a header is empty, you know the spec is not ready for review.

Writing Specs with EARS

EARS — the Easy Approach to Requirements Syntax — is the bridge between human intent and machine execution. It forces ambiguity out of requirements by replacing prose with structured clauses an LLM can parse as cleanly as a compiler parses code.

Developed by Alistair Mavin and adopted by aerospace and automotive engineering, EARS has five keywords that cover virtually every functional requirement you will write: When, While, Where, If, and Shall. The syntax is deliberately rigid because rigidity is exactly what prevents an agent from hallucinating intent.

When

Event-Driven Requirements

Use When for discrete triggers. "When the user clicks Submit, the system shall validate the payload." The event is singular and unambiguous.

While

State-Driven Requirements

Use While for continuous conditions. "While the connection is open, the system shall heartbeat every 30 seconds." Describes sustained behavior, not a one-off.

If

Conditional Requirements

Use If for branching logic. "If the API key is invalid, then the system shall return 401 before evaluating the rate limit." Nests inside When or While.

Where

Contextual Requirements

Use Where for scoped behavior. "Where the request originates from an internal subnet, the system shall bypass the rate limiter." Sets boundaries.

Why EARS matters for SDD

Large language models are pattern-completers. When you feed them structured patterns, they complete the right pattern. When you feed them vague prose, they complete whatever pattern is statistically nearest — which may not be what you meant. EARS gives the agent a grammar to follow, not just a topic to riff on.

As a practical rule: if you cannot restate a requirement as a When/If/While/Where clause followed by "the system shall," the requirement is not ready for an agent. It still has ambiguity that will compound into architectural drift.

From Vague to Verifiable

Vague (what not to write)EARS-compliant (what to write)
"The API should handle rate limiting." "When a client exceeds 100 requests in a 1-second window, the system shall return HTTP 429 and include a Retry-After header."
"Users must be authenticated." "When a request is received without a valid JWT, the system shall return 401 and shall not process the payload."
"The system should be fast." "When the database query returns more than 10,000 rows, the system shall paginate the response and shall return the first page within 200ms."
"Log errors properly." "If an unhandled exception occurs, the system shall write the stack trace to stderr with a UTC timestamp and shall return 500 to the client without exposing internal paths."

Common EARS Anti-Patterns

  • "Shall be able to" — Describes capability, not obligation. The agent may implement the feature as optional. Use "shall" alone for mandatory behavior.
  • "Shall consider" — Unverifiable. How do you test whether something was "considered"? Replace with a concrete action.
  • Multiple requirements in one sentence — "When X happens the system shall do Y and Z and also notify Q." Split into atomic sentences. One clause, one obligation.
  • Missing the trigger — A requirement that starts with "The system shall..." but never says When or If leaves the agent guessing about invocation context.

Nested Conditions

Real requirements rarely fit a single keyword. EARS supports nesting:

Nested EARS example
# Good: nested, unambiguous
When a payment request is received,
  If the account balance is sufficient,
    the system shall debit the amount and shall return 200.
  If the account balance is insufficient,
    the system shall return 402 and shall log the attempt.

# Bad: ambiguous ordering and missing branch
The system should process payments and handle errors.
Quick Reference

Before you approve any spec.md, run the EARS lint: can every requirement be prefixed with When/While/If/Where and end with a single "shall" action? If not, send it back for rewriting. This one habit prevents more agentic drift than any prompt-engineering trick.

Spec in Scrum & Kanban

A spec that lives outside your delivery rhythm is a spec that dies. SDD does not replace Agile — it needs to be wired into your existing ceremonies and board states. The goal is not more documentation; it is the right documentation at the right time.

Scrum Integration

In Scrum, the spec is both a gate and a contract. It gates work from entering a sprint, and it contracts the behavior of that work once development starts.

Backlog Refinement: Where specs are born

Refinement is the natural home for Phase 1 (Specify). When a story enters refinement, the agent — or the team — drafts the spec.md. The story is not "ready" until the spec passes a readability test: can another engineer, or another agent, implement this without asking clarifying questions? If not, the story stays in refinement.

Definition of Ready: The spec as a gate

Add a single line to your DoR: "The item has an EARS-formatted spec approved by the product owner and a technical reviewer." This prevents the common anti-pattern of pulling vague stories into a sprint and letting the agent guess the details under time pressure.

Sprint Planning: Review the spec, not just the title

During planning, the team reads the spec aloud (or the agent summarizes it), not the Jira title. Estimation should be based on spec complexity — number of EARS clauses, number of edge cases, number of cross-service touchpoints — not on gut feel.

During the Sprint: The spec is the sprint contract

Once the sprint starts, the approved spec is frozen for that iteration. If new information emerges, the change goes through a mini Phase 1: draft the amendment, review it, approve it. This prevents scope creep without creating a change-control bureaucracy. At sprint end, the demo validates against the spec's acceptance criteria, not a separate checklist written after the fact.

Retrospective: Did the spec match what we built?

Add one question to your retro: "Where did the spec diverge from the implementation, and why?" Consistent divergence means your EARS syntax is too loose, your review checkpoints are being skipped, or your stories are too large.

Scrum Anti-Pattern: The Spec Sprint

Dedicating an entire sprint to "writing specs" is BDUF in disguise. Specs should be written just-in-time — ideally 1–2 sprints ahead of implementation at most. Any spec written earlier than that is likely to go stale as the product learns from user feedback.

Kanban Integration

Kanban's flow-based model maps cleanly to SDD if you treat the spec as work that moves through its own column before hitting engineering.

Upstream queue: "Spec Needed"

Add a column upstream of "Ready for Dev" called Spec Needed. Cards sit here while Phase 1 runs. A card cannot enter "Ready for Dev" until it has a locked spec.md, plan.md, and tasks.md.

WIP limits on specs

Apply a WIP limit to the "Spec Needed" column. Overproducing specs that sit unread is inventory waste — they decay as the codebase evolves. A good starting limit is 2× your dev WIP limit: enough to keep the pipeline fed, not so many that you create a spec graveyard.

Pull criteria: What makes a spec ready?

Define explicit pull criteria for moving a card from "Spec Needed" to "Ready for Dev":

  • All EARS clauses have corresponding acceptance criteria.
  • The plan has been reviewed for architectural fit.
  • Tasks are sized to complete within your average cycle time.
  • No open clarification questions from the agent.
Watch For: Spec Inventory Waste

A spec that sits in "Spec Needed" for more than two weeks is probably stale. If your upstream WIP limit is consistently maxed out, you are writing specs faster than the team can absorb them. Lower the limit and focus on just-in-time refinement.

Spec Versioning & Lifecycle

What happens to a spec after the feature ships? Without a lifecycle policy, you get Böckeler's warning: "it is easy to end up with 100s of markdown files."

  • Archive on merge — Move spec.md to an archive/ folder when the feature ships. The spec is now read-only historical context.
  • Amend, do not overwrite — When requirements change, create spec-v2.md rather than editing the original. This preserves the audit trail of why the feature changed.
  • Delete after 90 days — If a spec has not been referenced in three months, it is either well-understood or forgotten. Delete it. Git history preserves it if you ever need it back.
  • Living specs only for living features — If a feature is actively maintained, its spec stays in the active folder and is updated alongside code changes. If the feature is stable, archive the spec.

CI/CD Integration

Human review gates in SDD map cleanly to normal git workflows if you wire them together:

  • PR checklist from tasks.md — A pre-commit hook or GitHub Action can parse tasks.md and auto-generate a PR checklist. The reviewer verifies each task is complete before approving.
  • EARS lint in CI — A simple regex check in your pipeline validates that every specs/**/*.md file contains at least one "shall" and no banned words ("should," "may," "consider"). Fail the build if the spec is malformed.
  • Spec-required gate — A GitHub Action that fails if a PR touches code in src/ but has no corresponding spec in .kiro/specs/ or specs/. This enforces spec-first at the merge gate.
  • Plan.md as PR comment — When plan.md is approved, paste its summary into the PR description. Reviewers see the intended architecture before they see the diff.
Practical Test

At any point in a sprint, ask: "If I handed this spec to a different agent who has never seen our codebase, could it implement the feature correctly?" If the answer is no, your spec has drifted from the code. Reconcile them before the sprint ends.

The Constitution & Standing Context

Every project needs two kinds of document: temporary specs that exist for one feature, and standing rules that apply to every change. The Constitution is your immutable foundation — the second kind.

As Birgitta Böckeler of Thoughtworks puts it: "general context are things like rules files, or high level descriptions of the product and the codebase… whereas specs [are] only relevant to the tasks that actually create or change that particular functionality." That standing-rules document is what this section covers.

What the Constitution Covers

A Constitution defines non‑negotiable principles that apply to every change — testing philosophy, security baselines, code style, and opinionated technology choices. This ensures organizational standards are baked into every project from the start.

constitution.md (generic template)
# Project Constitution — immutable principles
- All database mutations must use explicit transaction boundaries.
- All public endpoints must include active rate-limiting middleware.
- Unit tests are required for any newly created utility method.
- Write tests before implementing any business logic (TDD discipline).
- No raw SQL in controllers — all queries go through the repository layer.
- Secrets must be injected via environment variables, never hard-coded.

How the Constitution Fits into the Loop

  • You write it once at the start of the project.
  • The agent reads it at the beginning of every session — it is part of its permanent memory.
  • Every phase respects the Constitution: the agent will not propose a plan that violates it, and you use it as your own checklist during reviews.

Workspace Isolation New

Before the agent writes a single line of code, ensure it works on a clean branch or git worktree with a verified green test baseline. A dirty workspace or failing baseline makes it impossible to tell whether a test failure is from the new code or pre‑existing debt.

  • Why it matters: If the agent starts from a broken state, every fix it applies is a guess. You will burn tokens on regression fixes that should never have been the agent's problem.
  • How to do it: Use git worktree add ../feature-name main to create a fresh, isolated workspace. Run tests before the agent starts — if they fail, fix them first.
  • Tool support: Superpowers enforces this as a mandatory first step. Kiro CLI's /spec new does not automatically create a worktree, but you should treat it as a manual pre‑phase ritual.

This is harness engineering at its most basic: if you cannot trust the baseline, you cannot trust the diff.

Implementation by Tool

Kiro CLI — Steering Files

Store your Constitution in steering files inside .kiro/steering/. For example, put architecture rules in tech.md, structural rules in structure.md, and product rules in product.md. Since steering files are always loaded in every interaction, they automatically enforce your immutable rules on every change — no extra configuration needed.

.kiro/steering/tech.md — Kiro's Constitution
# Technology Constitution
- All database mutations must use explicit transaction boundaries.
- All public endpoints must include rate-limiting middleware.
- Write tests before implementing any business logic.
- All external API calls must have a 5-second timeout and circuit-breaker fallback.

Claude Code — CLAUDE.md

Place your Constitution directly in CLAUDE.md, which is read at the start of every session. For larger rulebooks, keep a separate constitution.md and reference it in CLAUDE.md using the @constitution.md syntax. This ensures Claude applies your rules to every task it touches.

CLAUDE.md — Claude's Constitution
# Project Constitution (loaded every session)
- All database mutations must use explicit transaction boundaries.
- All public endpoints must include rate-limiting middleware.
- Write tests before implementing any business logic.

# Reference a separate constitution file if it grows large
@constitution.md

Brownfield Bootstrapping

Both tools can generate a starter Constitution from an existing codebase instead of writing it blank:

  • Kiro: Use Generate Steering Docs (IDE button, CLI, or Web) to scan the repo and auto-draft product.md, tech.md, and structure.md from what is actually there.
  • Claude Code: Run /init in the repo before writing anything by hand — it detects your build system, test framework, and code patterns, and drafts a starter CLAUDE.md you refine from there.

Either way, do this before your first spec, not after — it is what stops Phase 1 from drafting requirements that quietly contradict how the codebase already works.

Constitution = Persistent Context

Whether you use Kiro's steering files or Claude's CLAUDE.md, the Constitution is your team's living rulebook. It outlasts any single feature spec and ensures every AI session starts with the same non‑negotiable standards. Update it rarely — treat it like a real constitution, not a daily checklist.

The 5-Point Scorecard

The 4-phase loop tells you how to run agentic work. It does not tell you whether what came out the other end was actually good. That is a separate question — and it is the one Andrej Karpathy's "agentic engineering" framework is really about: the discipline of judging agent output, not just producing it. Score every spec-driven task against these five dimensions before you approve the merge.

Two-Stage Review New

Stage 1 — Spec compliance: Does the diff implement what plan.md and tasks.md describe? Ignore code quality, style, and efficiency for this pass. The question is solely "did the agent build what was asked?"

Stage 2 — Code quality: Now check security, test coverage, style consistency, and elegance. Do not let the quality review distract you from catching a stage 1 mismatch. If the code is beautiful but solves the wrong problem, it is still a failure.

This separation is the single most effective habit for preventing "the agent did something impressive but unrelated to what I asked for."

Scorecard in Action: One Feature, Five Checks

The table above tells you what to check. What actually makes it click is seeing a real red flag next to the fix that catches it. Take the token-bucket rate limiter from Sheet 03 and run it through all five dimensions — this is the level of concreteness you are aiming for in your own reviews, not a vague "looks fine."

01

Spec Design

🚩 Red Flag

requirements.md just says "add rate limiting to the API" — no trigger, no boundary, no error format.

✅ Green Flag

"When a client exceeds 100 requests in a 1-second window, the system shall respond with 429 and a Retry-After header. If the request has no valid API key, then the system shall return 401 before evaluating the rate limit." Both the happy path and the auth-ordering edge case are explicit.

🔍 How You Catch It

Kiro: before typing "proceed," try restating each requirement as a When/If clause — if you cannot, it is not ready. Claude Code: same test, applied before approving Plan.

02

Diff Review

🚩 Red Flag

plan.md specifies a token bucket that refills continuously, but the diff implements a fixed window counter that resets every second — a quietly different, weaker algorithm that still passes the same tests.

✅ Green Flag

The diff contains a bucket struct with a token count and a last-refill timestamp — matching plan.md's stated approach line for line, not just its outcome.

🔍 How You Catch It

Kiro: as /spec run shows each diff, hold it next to design.md's algorithm section — not just "tests green." Claude Code: ask a reviewer sub-agent "does this diff implement what plan.md Section 3 describes, or a different approach that happens to pass the same tests?"

03

Eval Design

🚩 Red Flag

tasks.md says "add tests for rate limiter" — vague, so the agent writes one happy-path test and stops.

✅ Green Flag

The task's definition of done reads: "test: 101st request in a 1s window returns 429 with Retry-After ≥ 1; test: request with an invalid key returns 401 without consuming a token." Each line maps 1:1 to an EARS requirement.

🔍 How You Catch It

Kiro: check that every tasks.md verification line names a specific input/output pair, not "add tests." Claude Code: a CI gate that fails the merge if a task's test file does not reference its acceptance-criterion ID.

04

Security Oversight

🚩 Red Flag

The agent keys the rate-limit counter on client IP alone — reasonable-looking, but it breaks the moment two users share a corporate NAT or mobile carrier proxy, and it is trivially spoofed via X-Forwarded-For.

✅ Green Flag

The counter is keyed on the authenticated client/API-key ID, with IP used only as a secondary abuse signal.

🔍 How You Catch It

Kiro: a rule in .kiro/steering/tech.md — "never key security or quota logic on IP address alone" — is loaded every session, so Plan should propose the key-ID approach unprompted; if it does not, that is the flag. Claude Code: the same rule in CLAUDE.md, plus a dedicated pass: "review this diff only for identity and trust-boundary assumptions, ignore style."

05

Taste

🚩 Red Flag

The project already has lib/rate-limiter.ts, used by two other endpoints — the agent writes a second, subtly different implementation inline in the new middleware instead of importing it.

✅ Green Flag

The diff imports and extends the existing shared utility, or explicitly proposes replacing it with a stated reason.

🔍 How You Catch It

Kiro: the verifier agent is prompted specifically to grep for existing rate-limiting code before approving — duplication is an automatic flag. Claude Code: the reviewer sub-agent's prompt includes "search the codebase for existing implementations of this pattern before judging the diff done."

Save this once as a command and run it on every task. The prompt is tool-agnostic — adapt the save location to your workflow.

Why This Matters

Every one of these five failure modes looks identical on the surface: code that compiles, passes tests, and "works." That is exactly why a scorecard beats a gut check — the risk in agentic engineering is not broken code, it is code that quietly ships debt, security gaps, or architectural drift that only surfaces months later. A 5/5 on eval with a 1/5 on taste is still a liability, not a pass.

When the Loop Breaks

The 4-phase loop assumes a happy path. Production teams hit these failure modes weekly. Here is how to recover when the agent stalls, the spec contradicts itself, or the plan turns out to be impossible.

Failure: Agent Stuck in Phase 4 (Infinite Retry)

Symptom: The agent runs the same failing test 10+ times, tweaking the code slightly each time but never fixing the root cause.

Root cause: The task in tasks.md is too large or the definition of done is vague. The agent is optimizing locally (make the test green) without understanding globally (why it fails).

Recovery:

  1. Stop the agent. Do not let it burn more tokens.
  2. Read the failing test and the last three diffs. Identify the actual root cause — is it a missing dependency? A wrong mock? A race condition?
  3. Split the task into two smaller tasks: one to reproduce the failure reliably, one to fix it.
  4. Update tasks.md with the split, approve it, and restart from the smaller task.

Prevention: Enforce the 2–5 minute granularity rule from Sheet 04. If every task is small enough to complete in a single focused pass, the agent never has enough context to spin indefinitely.

Failure: Spec Contradicts Itself

Symptom: During Phase 4, the agent reports that requirement R3 says "return 401" and requirement R7 says "return 403" for the same condition.

Root cause: The clarification pass in Phase 1 missed a logical conflict, or the spec was amended mid-sprint without checking for collisions.

Recovery:

  1. Do not let the agent guess which requirement wins. That is a human decision.
  2. Update spec.md to resolve the conflict explicitly. Add a note: "R7 supersedes R3 for invalid API keys."
  3. Re-run Phase 2 (Plan) to verify the fix does not break the architecture.
  4. Re-run Phase 4 from the affected task forward.

Failure: Plan is Technically Infeasible

Symptom: The plan proposes a library your security team has banned, or a database pattern that violates your existing schema constraints.

Root cause: The Constitution was not loaded, or the agent did not check it against the plan before proposing.

Recovery:

  1. Reject the plan immediately. Do not let the agent proceed to tasks.
  2. Add the missing constraint to the Constitution so it cannot happen again.
  3. Ask the agent to regenerate the plan with the constraint explicitly stated.

Failure: Diff is Correct, But the Spec Was Wrong

Symptom: The implementation perfectly matches the spec, but the spec described the wrong behavior. The agent did exactly what you asked — you just asked for the wrong thing.

Root cause: This is not an agent failure. It is a spec failure. The EARS requirement was syntactically correct but semantically wrong.

Recovery:

  1. Update spec.md first. Never patch the code and leave the spec stale.
  2. Re-run the affected phases. If the change is small, you may only need to re-run Phase 4 for the affected task.
  3. Add the misinterpretation to your retro notes: why did the spec say the wrong thing, and how do you catch it earlier next time?
Recovery decision tree: fix the spec first, then the code
The Golden Rule of Recovery

When in doubt, fix the spec first. Patching the code and leaving the spec stale creates the exact drift SDD was designed to prevent. A 5-minute spec edit now saves a 5-hour debugging session later when the next agent reads the stale spec and builds the wrong thing again.

The Three Loop Exit Failures

Most loop failures are not crashes — they are mis-exits. The agent stops, but at the wrong time, for the wrong reason, or not at all. Every SDD phase gate is an exit condition; if it is vague, the loop breaks in one of three ways:

  • Stops too early — The agent hits a surface-level signal (one test passes) and declares success before the task is actually done. Common when the Definition of Done in tasks.md says "add tests" instead of naming specific input/output pairs.
  • Loops indefinitely — No convergence detection. The agent burns tokens retrying the same failed approach because the failure criterion is not distinct from the retry trigger. Fix: cap retries at 3, then escalate to human.
  • Declares success prematurely — The completion criterion is subjective. "The report is written" vs. "The report contains an executive summary, three supporting sections each with at least two data citations, and passes a relevance check." EARS requirements exist precisely to prevent this.

The fix for all three is the same: write the exit condition before the loop starts. In SDD, that means every tasks.md entry needs a concrete, observable Definition of Done — not a vibe check.

SDD vs. TDD vs. BDD

SDD gets confused with test-driven and behavior-driven development constantly, because all three share the same instinct: define correctness before you write the implementation. The difference is what document is treated as the canonical, load-bearing artifact.

ApproachCanonical artifactCore questionWhere tests come from
TDDThe test file"Write the failing test first."Tests come first; implementation follows to satisfy them.
BDDThe Gherkin scenario"Describe behavior in business language first."Scenarios written collaboratively with stakeholders, then automated.
SDDThe full specification"Write intent, architecture, edge cases, and constraints — then let the agent produce code, tests, and docs."Generated from the spec, not written ahead of it by a human. The Test Plan section in spec.md (see Sheet 04) defines the tests before the agent writes a single line of implementation.

How They Work Together

SDD does not replace your existing practice — it changes who owns which part of the test pyramid. The spec generates the acceptance layer (integration / end-to-end). You still own the unit layer. Here is exactly what changes and what stays the same.

Your Current PracticeWhat SDD ChangesWhat Stays the Same
TDD The spec provides the acceptance criteria your unit tests must satisfy. You know exactly what "passing" looks like before you write the first red test. Red-green-refactor cycle. You still write unit tests by hand. The spec does not replace your test file — it replaces the vague Jira ticket you used to guess the requirements from.
BDD The agent writes EARS requirements instead of you writing Gherkin by hand. The scenarios are stricter and machine-parseable, but the stakeholder-collaboration goal is identical. Given-When-Then thinking. Stakeholder review of behavior. The spec is the scenario — just written in a syntax an agent can execute, not just a human can read.
Neither Start with SDD. The spec's acceptance criteria and Test Plan (Sheet 04) will naturally generate integration tests. Add unit tests where the spec is too coarse-grained. Nothing — you are building from a clean slate. Use the Build-Test-Harden sequence in Sheet 14.

The Hard Rule: Who Owns What

  • Integration tests — generated by the agent from the spec's Test Plan and acceptance criteria. They prove the feature works end-to-end. You review them, you do not write them.
  • Unit tests — written by you. The spec is too coarse-grained to dictate every branch condition, mock, and edge case inside a single function. Your TDD discipline still applies here.
  • EARS requirements — written collaboratively (you + agent). They are the contract both sides agree to before code is written.
Practical Test

If your team already does TDD, add one line to your process: "No red test without a corresponding EARS requirement in the spec." The spec becomes your source of testable requirements, and TDD becomes the mechanism for proving the implementation satisfies them. The two practices reinforce each other rather than competing.

  • Design validation — check the plan against the Constitution and existing codebase.

  • Bite-sized plans — tasks are capped at 2–5 minutes (same granularity rule as Sheet 04).
  • Subagent-driven execution — separate agents for planning and implementation.

  • Branch cleanup — automated cleanup of worktrees and branches after merge.

If you want zero setup and an opinionated structure, start with Kiro CLI. If you already use Claude Code and want flexibility, start with custom commands or extensions. Vibe Coding vs. Spec-Driven: The Honest Call

SDD provides structural reliability, but it is genuine overhead for small tasks — turning a one-line fix into a web of user stories and acceptance criteria is its own anti-pattern, sometimes called "a sledgehammer to crack a nut."

Reach for Spec-Driven when:

  • You are writing production systems meant to scale and be maintained long-term.
  • Multiple engineers, or multiple parallel agents, work the same codebase at once.
  • You must enforce security profiles, data constraints, compliance rules, or design tokens precisely.
  • The system involves migrations, multi-service topologies, or intricate state machines.

Default to Vibe Coding when:

  • You are building throwaway code, isolated proofs-of-concept, or rapid wireframes.
  • The task is visual and needs fast, intuitive tweaking rather than a locked spec.
  • It is a minor bug fix — a full pipeline here is the sledgehammer problem above.
  • You are exploring an unfamiliar stack and do not yet know what you actually want.
A Practical Test

One heuristic experienced SDD practitioners use cuts through the ambiguity fast: if you would be annoyed to find the agent interpreted your requirement differently than you meant, write the spec. If a quick follow-up prompt would fix it just fine, skip the spec and prompt directly. It is a five-second gut check, and it is usually right.

The Honest Limits

Every team adopting SDD should walk in aware of where it currently breaks down.

1. The brownfield adoption gap

SDD frameworks shine on greenfield projects where the agent builds from a clean slate. Dropping a full SDD pipeline onto a large legacy codebase in one go rarely works — it needs progressive, iterative adoption, feature by feature, not a big-bang rewrite. Both tools have a specific onboarding step for this (see Sheet 11), but even with it, treat the first few brownfield specs as trust-building exercises, not a reason to spec the entire legacy system at once.

2. The Markdown Monster risk

Adopt complex spec workflows without changing how your team actually collaborates, and you get documentation overhead instead of clarity. If a simple change spawns hundreds of verbose planning files, you are now spending more time reviewing prose than reviewing the code it produced. As Böckeler notes, "it is easy to end up with 100s of markdown files." The fix: archive specs after merge, delete stale ones after 90 days, and keep specs just-in-time (see Sheet 06).

3. Semantic diffusion

As "spec-driven" gets popular, plenty of people use "spec" as a synonym for "a detailed prompt." That is not SDD — true SDD requires an execution engine that treats the specification as an actionable, verifiable source of truth, not just a longer prompt.

4. The heavy-upfront-planning critique

The Thoughtworks Technology Radar has placed SDD in its "Assess" ring — worth evaluating, not yet a default recommendation — and specifically flags a risk of the practice tilting back toward big up-front specification and big-bang releases, the same anti-pattern Agile spent two decades pushing teams away from. SDD is compatible with Agile when specs stay living, lightweight artifacts updated inside normal sprints — the moment they calcify into Waterfall-style documentation, you have lost the point.

5. The human-gates debate

Some argue that as agents improve, manual approval gates become pure friction. The counter-argument is simpler: production software carries risk, compliance, and legal accountability that someone has to own. An agent's growing ability to create value scales in lockstep with its ability to amplify a mistake. Human gates exist not because agents cannot do the work, but because someone must be liable when it is wrong. Where you land depends on what you are building and who pays for the outage.

Bottom Line

SDD is a genuine improvement over unstructured prompting for anything production-grade — but it is a discipline, not a silver bullet. It still requires someone to write a good spec, and a bad spec compiled perfectly is still a bad system.

First Project Tip

Run your first pass on something small and real — a rate limiter, a webhook validator, a single CRUD endpoint. Learn the rhythm of the workflow before you trust it on anything with production stakes.

The Build-Test-Harden Sequence

Adopt SDD in three deliberate stages, not all at once:

  1. Build the loop first. Run one complete 4-phase cycle on a small, real feature (a rate limiter, a webhook validator). Do not worry about the Constitution or CI gates yet. Learn the rhythm of draft-review-approve.
  2. Build the harness next. Once the loop feels natural, add your Constitution, steering files, and the 5-point scorecard. This is where you prevent the agent from doing damage, not where you teach it what to do.
  3. Harden both together. Add CI gates, spec versioning, and the verifier pattern. Track scorecard metrics over time. The loop and the harness improve each other — a tighter loop reveals harness gaps, and a stronger harness lets the loop run with less human friction.

Teams that try to implement the full harness before they understand the loop usually over-engineer the constraints and under-engineer the workflow. Build, then test, then harden.

Annotated Example: Token-Bucket Rate Limiter

This is the complete spec for the rate limiter mentioned in Sheet 03. Every section is annotated to explain why it is written this way. Copy the structure, adapt the content.

requirements.md Updated

specs/rate-limiter/requirements.md
# Rate Limiter Middleware

## Background
# Why this exists: prevents abuse of public API endpoints.
# Context: deployed as Express middleware, must not break existing routes.

## EARS Requirements
# R1: The trigger (When) is explicit. The agent knows exactly when to activate.
When a request is received, the system shall count that request
against the authenticated client's token bucket.

# R2: The edge case (If) is explicit. The agent cannot guess the error format.
If the client's token bucket is empty, the system shall return
HTTP 429 Too Many Requests with a Retry-After header set to the
number of seconds until the next token is available.

# R3: Auth ordering is explicit. Prevents the IP-spoofing bug from Sheet 08.
If the request has no valid API key, the system shall return
HTTP 401 Unauthorized before evaluating the rate limit.

# R4: Continuous state (While) defines sustained behavior.
While the server is running, the system shall refill each client's
bucket at a rate of 100 tokens per second, up to a maximum burst
of 150 tokens.

## Non-goals
# Explicitly excluded to prevent scope creep.
- No per-IP rate limiting (handled by WAF).
- No admin dashboard for viewing bucket state.
- No distributed rate limiting across data centers.

## Assumptions
# Decisions already made — the agent should not re-decide these.
- In-memory storage is sufficient for single-node deployment.
- API keys are validated by an upstream auth middleware before we see the request.
- Clock drift is negligible; we use monotonic time for refill calculations.

## Constraints
- Must use the existing lib/rate-limiter.ts utility; do not write a second implementation.
- Must not add external dependencies.
- Must support horizontal deployment (stateless node design).

## Reference implementation
# Link to spike that proves token-bucket works in this stack.
See _spec/spikes/reference/token-bucket-spike/ for a working prototype.

## Test Plan
# Named tests with exact inputs/outputs — written before implementation.
- T1: 100 requests in 1 second → all return 200.
- T2: 101st request in same second → returns 429 with Retry-After ≥ 1.
- T3: Request with invalid API key → returns 401, no token consumed.
- T4: After 1 second of no requests, bucket refills → next request returns 200.
- T5: Load test: 10,000 requests over 10 seconds → no memory leak, all requests within 200ms.

## Acceptance Criteria
- AC1: 100 requests in 1 second succeed. The 101st returns 429.
- AC2: A request with an invalid key returns 401 without consuming a token.
- AC3: After 1 second of no requests, the bucket refills and requests succeed again.
- AC4: All existing integration tests continue to pass.

## Out of Scope
- Per-IP rate limiting (handled by WAF).
- Admin dashboard for viewing bucket state.
- Distributed rate limiting across data centers.

design.md

specs/rate-limiter/design.md
# Rate Limiter — Technical Design

## Architecture Decision
# Why token bucket: satisfies burst + sustained rate requirements (R4).
# Why not fixed window: fixed window allows burst at window boundaries.
Use a token-bucket algorithm with a floating-point token count and
last-refill timestamp stored in an in-memory Map keyed by API-key ID.

## Data Flow
1. Request arrives → middleware extracts API key from Authorization header.
2. If key is invalid → return 401 (R3).
3. If key is valid → look up bucket in Map. If missing, create with 150 tokens.
4. Calculate elapsed time since last refill. Add tokens at 100/sec (R4).
5. If tokens ≥ 1 → decrement and call next().
6. If tokens < 1 → return 429 with Retry-After = ceil(1 / refillRate) (R2).

## Component Design
- src/middleware/rate-limiter.ts — new file, the middleware entry point.
- src/lib/token-bucket.ts — new file, bucket math (refill logic).
- lib/rate-limiter.ts — existing shared utility, imported and extended.

## Dependencies
- None. Uses native Node.js process.hrtime.bigint() for high-resolution timing.

## Risk Assessment
- Memory leak: Map grows unbounded if clients never reappear.
  Mitigation: prune entries older than 1 hour via a periodic sweep.
- Clock skew: hrtime is monotonic, safe for refill calculations.
- Horizontal scaling: in-memory Map is node-local. If we scale horizontally
  later, we will need Redis. Out of scope for this iteration.

Why This Structure Works

  • requirements.md contains only behavior — no implementation hints. The agent cannot drift into a "better" algorithm because the constraints explicitly ban it. The Non-goals, Assumptions, and Reference implementation sections prevent the agent from re-deciding choices you have already made.
  • design.md contains the algorithm choice and risk assessment. If the diff shows a fixed-window counter instead of a token bucket, the reviewer catches it immediately by comparing diff to design.md Section 1.
  • tasks.md maps 1:1 to acceptance criteria and the Test Plan. AC1 → T03 test case. AC2 → T03 test case. Each task has an estimated time that enforces the 2–5 minute granularity rule.
